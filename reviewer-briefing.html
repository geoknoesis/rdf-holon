RDF-H 0.8 Reviewer Briefing

October 21, 2026 · Stephane Fellah · Geoknoesis LLC

RDF-H is a community draft for organizing RDF statements into identifiable content units called holons. The specifications, fixtures, and reference implementations come from the editors' organization. The next evidence needed is an implementation by a party that did not write them, built from the normative text.

What RDF-H defines

A designated metadata context M explicitly registers holons and records their graph mappings, optional administrative parents, content imports, and shape imports. Content-only management assertions never become authoritative declarations. A holon has at most one administrative parent; several roots are allowed.

The dataset profile extracts content from named graphs. The reifier profile uses RDF 1.2 reifiers and h:inHolon. Direct scope selects one holon's content; aggregated scope adds descendants; visible scope additionally adds the selected holon's direct imports. Imports are single-hop and do not inherit descendants or further imports. An attributed dataset retains one named graph per selected holon.

Every filed statement must be asserted in G, the union of source assertions and M. A base assertion supplied only in M satisfies this invariant. This union is an RDF-H interpretation: ordinary SPARQL default-graph queries retain their usual graph-selection behavior and do not automatically read G.

The harness compares exact error conditions where a fixture declares ht:expectedCondition, in addition to the broad category. All 15 processing conditions have such fixtures. It checks converted membership and mapping validity before comparing content and metadata. The requirement trace contains 21 reviewed groups; this is not exhaustive base-language coverage.

Passing these project-authored cases establishes agreement with these fixtures. It does not establish independent interoperability. Serializer tests reparse output with the same implementation; matching parser/writer defects remain possible. The inherited Turtle 1.2 suite has not been run here. The Python adapters are experimental and do not implement every RDF 1.2 term or query feature.

Corrections following the first review

  • Serialization rejects unrepresentable-context when expanded output would promote an assertion absent from M into an active declaration. It does not invent memberships to hide that assertion.
  • Conversion rejects unrepresentable-conversion when preserving M and each holon's content is impossible. Distinct contents must not be merged into a shared target graph.
  • Retained dataset assertions using h:inHolon can become active in a reifier target. Converters check the target and reject invalid or changed content before returning success.
  • The base-assertion rule consistently checks G = source assertions ∪ M.
  • Error fixtures check specific conditions; counts and dependency statuses are corrected across the documents.

The conversion and serialization failures above are operation-specific errors; they do not add entries to the algorithm's 15 scope-resolution and validation conditions.

Design decisions to challenge

  • One parent. The forest simplifies administration. A DAG could also have unambiguous set-union aggregation. Imports reuse direct content and do not fully substitute for a second parent's descendant aggregation.
  • No automatic ancestor scope. A part imports its parent explicitly when it needs the parent's direct content. Does this suffice for realistic contexts?
  • Single-hop imports. Does explicit enumeration remain manageable for substantial dependency structures?
  • Always-asserted filed statements. Hypothetical or unasserted contexts are outside the model. Is that restriction acceptable?
  • Global validity checks. An unrelated hierarchy defect can fail aggregated and visible requests. Should deployments partition M into separate failure domains?
  • Shared graph mappings. Several dataset holons may share identical content. Conversion must reject incompatible contents under such mappings.
  • Attribution. Named graphs identify holons, including blank-node descendants and imports; they do not preserve individual occurrence provenance.
  • Serializer choices. Folding is optional and block grouping is not canonical. Compare preservation guarantees rather than identical text or blocks.
  • Publication. Review the proposed text/turtle-h media type, .ttlh extension, version IRIs, and namespace continuity.

Dependencies and open work

The drafts pin RDF 1.2 Concepts, April 7, 2026 (Candidate Recommendation Snapshot), RDF 1.2 Semantics, September 24, 2026 (Candidate Recommendation Draft), Turtle 1.2, October 7, 2026 (Working Draft), and SPARQL 1.2 Query, October 11, 2026 (Working Draft). They have different maturity levels and must be reassessed before stabilization.

Independent implementations and EARL reports are still needed. Namespace redirects, stable version artifacts, media-type registration, inherited-language testing, and publication of the Java codec remain release work. SPARQL-H selects its root by constant IRI; blank-node roots cannot be selected directly through its syntax.

The optional service profile defines no standard transport. Its current suite does not exercise deployment behavior. A documented integration adapter can nevertheless test dataset-selector conflicts, federation policy, filtering disclosures, forbidden network requests, and read-only behavior. Trust in M requires deployment review.

Review questions

  1. Can you implement the processing algorithm from its inputs, steps, and error table? Does explanatory text contradict it?
  2. Can you name a valid input with undefined resolution, conversion, or serialization behavior?
  3. Do successful conversions preserve M, the registry, every CG(H), and the declared assertion level?
  4. Do serializer outputs preserve the G/M boundary, including nonfoldable control-predicate content?
  5. Does attribution behave correctly with blank-node descendants, shared graphs, subqueries, trailing VALUES, and SERVICE?
  6. Do the security rules match who may edit M and content in your deployment?
  7. Can your independent implementation execute all 178 cases and publish an EARL report, including failures and skips?
