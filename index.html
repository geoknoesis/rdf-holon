This document specifies RDF-H, a vocabulary and modeling pattern for representing holarchic structures within the Resource Description Framework 1.2 [[RDF12-CONCEPTS]]. A holarchy is a system of holons, where each holon is a resource that is simultaneously a whole in itself and a part of a larger whole. RDF-H provides a semantically precise and structurally native method for representing nested, contextual, and compositional knowledge by building directly on the RDF 1.2 reifier model (rdf:reifies and triple terms). It introduces a core vocabulary centered on the h:inHolon property — which links a triple-occurrence's reifier to the holon that contains it — together with a formal mereological hierarchy of part-whole relations. The specification also proposes Turtle-H, a syntactic sugar over Turtle 1.2 [[RDF12-TURTLE]] providing a concise @holon directive for defining holons. By grounding containment in formal mereology and remaining fully within the RDF 1.2 abstract syntax, RDF-H enables the robust modeling of digital twins, cyber-physical systems, fine-grained access control policies, and other domains requiring a native understanding of "wholes-within-wholes."

This document is a draft proposal produced by Geoknoesis LLC. It is not an official specification produced by the W3C, nor is it an official work item of any W3C Group. This document is published with the aim of gathering feedback from the community for potential future submission to and standardization by the W3C.

This proposal builds on the RDF 1.2 family of specifications ([[RDF12-CONCEPTS]], [[RDF12-SEMANTICS]], [[RDF12-TURTLE]]), which are at Candidate Recommendation status at the time of writing. In particular, RDF-H depends on the RDF 1.2 reifier model, the rdf:reifies predicate, the triple-term syntax <<( s p o )>>, and the Turtle 1.2 reified-triple sugar << s p o >> and annotation syntax {| ... |}. Should those RDF 1.2 designs change before final Recommendation, this document will be updated accordingly.

Introduction and Motivation

The Resource Description Framework (RDF) provides a powerful, graph-based data model for representing information about resources and the relationships between them. Its core structure, a set of subject-predicate-object triples, creates a directed, labeled graph that is flexible, extensible, and web-scalable. However, the "flat" nature of this graph, where all triples exist at the same structural level, presents significant challenges when modeling systems that possess inherent compositional or contextual hierarchies.

The key words MUST, MUST NOT, SHOULD, and MAY in this document are to be interpreted as described in [[RFC2119]].

The Need for a Compositional Modeling Pattern

Many real-world and conceptual domains are fundamentally compositional. A car is a whole composed of parts like an engine and wheels; the engine, in turn, is a whole composed of its own parts. A digital twin of a factory floor is a whole that contains digital twins of individual assembly lines, which in turn contain twins of robotic arms. In systems biology, a cell contains organelles, which contain molecular complexes. In all these cases, the identity, boundary, and integrity of a subsystem (the "part") are as crucial as the relationships that exist within it.

While RDF can describe these part-whole relations using predicates (e.g., ex:engine ex:partOf ex:car), it lacks a simple, standardized pattern to represent this containment in a way that is both structurally intuitive and semantically rich. Existing approaches require developers to adopt specific modeling conventions or use mechanisms that were designed for related but distinct purposes. This leads to semantic ambiguity, complex queries, and a disconnect between the intuitive structure of the domain and its representation in the graph. This specification for RDF-H introduces a vocabulary and modeling pattern to address this gap, providing a native, semantically grounded way to model structural composition directly within the graph.

Limitations of Existing Approaches: A Comparative Analysis

The need for a new standardized pattern is best understood by examining the limitations of current RDF mechanisms for grouping, contextualizing, and annotating data.

Standard (Legacy) Reification

The original RDF specification provided a vocabulary (rdf:Statement, rdf:subject, rdf:predicate, rdf:object) for reification, allowing a statement to be treated as a resource. This approach has several well-documented drawbacks, including verbosity (four extra triples per annotation) and weak semantics (asserting the reification does not assert the original triple).

In RDF 1.2 [[RDF12-CONCEPTS]] this legacy reification vocabulary has been effectively superseded by the reifier model — a single rdf:reifies predicate linking a reifier (an IRI or blank node) to a triple term. The legacy rdf:Statement vocabulary remains in the namespace for backward compatibility but is independent of, and not used by, the RDF 1.2 reifier machinery on which RDF-H is built.

RDF 1.2 Triple Terms and Reifiers

RDF 1.2 introduces triple terms (terms that denote a triple, written <<( s p o )>> in Turtle 1.2 and constrained to the object position) together with the rdf:reifies predicate, which links a reifier (an ordinary IRI or blank node) to a triple term [[RDF12-CONCEPTS]]. This machinery makes it possible to attach metadata to a particular occurrence of an asserted triple without using the older rdf:Statement reification vocabulary.

While immensely useful, this is a mechanism, not a pattern. It is designed to attach metadata to individual edges in the graph, answering "What can be said about this specific relationship?" It does not, by itself, provide a standardized way to group a set of relationships into a containing whole. Without a standard like RDF-H, developers would attach reifiers to different, incompatible properties (e.g., ex:hasContext, ex:isAbout, ex:partOfGroup) to achieve the same goal, fragmenting the ecosystem. RDF-H proposes a single, standard reifier-attached property (h:inHolon) for this purpose.

Named Graphs (RDF Datasets)

Named graphs are the most common mechanism in RDF for grouping triples [[RDF11-DATASETS]]. However, a deeper analysis reveals that it is fundamentally a data management feature, not a resource modeling primitive, with critical limitations for representing holonic structures:

  • Dataset-Level Partitioning, Not Resource-Level Composition: Named graphs partition the entire triple store into distinct, named sets of triples. In contrast, RDF-H establishes a compositional relationship between resources within a single, unified graph.
  • Ambiguous Semantics: The semantics of a graph name are notoriously underspecified. This ambiguity makes named graphs unsuitable for precise, model-theoretic representation of part-whole relations.
  • Querying Paradigm: Querying across named graphs in SPARQL requires the GRAPH clause, which changes the active graph. This is a meta-level operation on the dataset, not a traversal of a relationship within the graph.

RDF-H, as proposed in this specification, offers a solution that is semantically precise, operates at the resource level, and is designed for native traversal-based querying.

Conformance Criteria

This specification defines two classes of conformance.

A conformant RDF-H Processor MUST:

  1. Satisfy all conformance criteria for a fully conformant RDF 1.2 processor [[RDF12-CONCEPTS]], including support for triple terms, the rdf:reifies predicate, and the Turtle 1.2 syntactic forms for reified triples and annotation blocks [[RDF12-TURTLE]].
  2. Correctly parse and serialize the Turtle-H syntax defined in , translating it to and from its standard RDF 1.2 representation.
  3. SHOULD support an entailment regime that respects the RDFS and OWL semantics of the RDF-H vocabulary defined in . At minimum, an RDF-H processor SHOULD implement the h-holon-type entailment rule (see ) and rdfs:subPropertyOf traversal for the h:partOf hierarchy.

A conformant RDF-H Graph MUST:

  1. Be a valid RDF 1.2 graph.
  2. Adhere to the modeling patterns defined in this specification.
  3. Not contain any cycles in its part-whole relationship hierarchies. This requirement is operationalized by the h:AcyclicPartConstraintComponent defined in ; a graph is non-conformant if that constraint reports any violation when applied to its h:Holon instances under the entailment regime supported by the validating processor.

The acyclicity requirement is also captured at the OWL DL level for the strict (non-transitive) immediate-part properties: h:directlyPartOf and its sub-properties h:componentOf and h:memberOf are declared owl:AsymmetricProperty and owl:IrreflexiveProperty, so any graph containing a cycle in those properties is OWL-inconsistent. Acyclicity of the transitive properties (h:partOf, h:substanceOf, h:portionOf) cannot be expressed in OWL DL — see for the rationale — and is enforced by the SHACL component referenced above.

The RDF-H Vocabulary

This section defines the core vocabulary for the RDF-H modeling pattern. The vocabulary namespace is https://w3id.org/rdf-h#, bound by convention to the prefix h:.

Core Class and Property

h:Holon
The class of all holons. Membership in h:Holon means precisely that the resource is permitted to appear as the object of an h:inHolon triple — i.e., that it may serve as a containing whole for one or more triple-occurrences (each represented by a reifier in the sense of [[RDF12-CONCEPTS]]). Class membership is also entailed by the rdfs:range axiom on h:inHolon: ?h is inferred to be an h:Holon whenever ?r h:inHolon ?h appears in the graph (see ).
Conceptually, a holon is a resource that is simultaneously a whole composed of parts and (typically) a part of a larger whole — but no axiom of h:Holon requires either: a holon may be empty (containing no h:inHolon-linked relationships) or top-level (not itself a part of any other holon).
h:inHolon
An object property that links an RDF 1.2 reifier — an IRI or blank node related to a triple term via rdf:reifies — to the holon that contains the corresponding triple-occurrence. The subject of h:inHolon is therefore the reifier (which identifies one occurrence of an asserted triple); the object is the containing holon. Its rdfs:range is h:Holon. No rdfs:domain is declared, because RDF 1.2 places no class restriction on reifiers [[RDF12-CONCEPTS]]. Note that this property does not use the older rdf:Statement reification vocabulary, which is independent of the RDF 1.2 reifies / triple-term machinery.
In Turtle 1.2 [[RDF12-TURTLE]] the bare-brace syntax << :s :p :o >> (a reified triple) expands to a fresh blank-node reifier _:b rdf:reifies <<( :s :p :o )>>; only triple terms — written <<( s p o )>> with parentheses — appear as objects, never as subjects. RDF-H reuses this reifier sugar so that h:inHolon is always asserted on an IRI or blank node.

The Part-Of Hierarchy

Future direction. The mereology vocabulary defined in this section (h:partOf, h:hasPart, h:directlyPartOf, h:hasDirectPart, and the component/member/substance/portion sub-properties) is logically separable from the holon machinery defined in the rest of this document. A future revision MAY extract it into a standalone mereology vocabulary specification at a sibling namespace, with RDF-H then importing it. The IRIs and semantics defined here are intended to remain stable across that potential extraction; in particular, the namespace IRI of any extracted vocabulary will be chosen so that simple IRI rewriting suffices for migration. Community feedback on whether to perform that extraction — and on a preferred sibling namespace — is explicitly invited.

To provide semantic precision, RDF-H defines a hierarchy of part-whole relationships using rdfs:subPropertyOf and owl:inverseOf. This lets modelers be specific while keeping queries general. [[OEP-PARTWHOLE]]

Two top-level properties anchor the hierarchy:

  • h:partOf is transitive, providing the closure used for "is somewhere in the part hierarchy of" queries.
  • h:directlyPartOf is non-transitive, asymmetric, and irreflexive, capturing the immediate (one-step) part relation between a whole and a part. It is a sub-property of h:partOf.

Why two top-level properties? OWL 2 DL forbids combining owl:TransitiveProperty with owl:AsymmetricProperty or owl:IrreflexiveProperty on the same property (see the global restrictions on simple roles in [[OWL2-SYNTAX]] and [[OWL2-DIRECT-SEMANTICS]]). To remain in OWL DL while still expressing the full mereological intent, RDF-H separates the closure-providing property (h:partOf, transitive) from the strict immediate-part relation (h:directlyPartOf, asymmetric and irreflexive). Acyclicity of h:partOf itself — and of its transitive sub-properties h:substanceOf and h:portionOf — is enforced by SHACL (see ) rather than by an OWL axiom.

Property characteristics such as owl:TransitiveProperty, owl:AsymmetricProperty, and owl:IrreflexiveProperty are not inherited via rdfs:subPropertyOf in OWL. Each property in the hierarchy therefore declares its own characteristics explicitly.

h:partOf / h:hasPart
The top-level super-property for all part-whole relations. Use it to query the transitive closure of the part hierarchy. h:hasPart is the inverse of h:partOf.
Characteristics: Transitive. (Acyclicity enforced by SHACL.)
h:directlyPartOf / h:hasDirectPart
The immediate-part relation between a part and the whole that contains it directly. Use this when you want to assert a one-step containment without engaging transitive closure semantics. h:hasDirectPart is the inverse of h:directlyPartOf.
Characteristics: Non-transitive, asymmetric, irreflexive.
h:componentOf / h:hasComponent
A sub-property of h:directlyPartOf for functional or structural parts (e.g., an engine is a component of a car). This relationship is essential for preserving the distinct levels of a holarchy. h:hasComponent is the inverse of h:componentOf.
Characteristics: Non-transitive, asymmetric, irreflexive.
h:memberOf / h:hasMember
A sub-property of h:directlyPartOf for elements in a collection or group where the whole is an aggregate of its members (e.g., a player is a member of a team). h:hasMember is the inverse of h:memberOf.
Characteristics: Non-transitive, asymmetric, irreflexive.
h:substanceOf / h:hasSubstance
A sub-property of h:partOf for material composition (e.g., clay is a substance of a brick). A part of the substance is also a part of the whole. h:hasSubstance is the inverse of h:substanceOf.
Characteristics: Transitive. (Acyclicity enforced by SHACL.)
h:portionOf / h:hasPortion
A sub-property of h:partOf for segments of a continuous whole (e.g., a slice is a portion of a pie). A part of the portion is also a part of the whole. h:hasPortion is the inverse of h:portionOf.
Characteristics: Transitive. (Acyclicity enforced by SHACL.)

Ontology Definition (Turtle):

@prefix h: <https://w3id.org/rdf-h#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .

# Top-level transitive part-of (closure for queries; acyclic via SHACL)
h:partOf a owl:ObjectProperty, owl:TransitiveProperty .
h:hasPart a owl:ObjectProperty, owl:TransitiveProperty ;
    owl:inverseOf h:partOf .

# Direct (immediate) part — non-transitive, asymmetric, irreflexive
# (DL-safe complement to the transitive h:partOf)
h:directlyPartOf a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:partOf .
h:hasDirectPart a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:hasPart ;
    owl:inverseOf h:directlyPartOf .

# Non-transitive sub-properties of h:directlyPartOf
h:componentOf a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:directlyPartOf .
h:hasComponent a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:hasDirectPart ;
    owl:inverseOf h:componentOf .

h:memberOf a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:directlyPartOf .
h:hasMember a owl:ObjectProperty,
        owl:AsymmetricProperty,
        owl:IrreflexiveProperty ;
    rdfs:subPropertyOf h:hasDirectPart ;
    owl:inverseOf h:memberOf .

# Transitive sub-properties of h:partOf (acyclic via SHACL, like h:partOf)
h:substanceOf a owl:ObjectProperty, owl:TransitiveProperty ;
    rdfs:subPropertyOf h:partOf .
h:hasSubstance a owl:ObjectProperty, owl:TransitiveProperty ;
    rdfs:subPropertyOf h:hasPart ;
    owl:inverseOf h:substanceOf .

h:portionOf a owl:ObjectProperty, owl:TransitiveProperty ;
    rdfs:subPropertyOf h:partOf .
h:hasPortion a owl:ObjectProperty, owl:TransitiveProperty ;
    rdfs:subPropertyOf h:hasPart ;
    owl:inverseOf h:portionOf .

Exclusion of Other Relationship Types

It is a deliberate design choice for the RDF-H vocabulary to focus exclusively on composition (h:inHolon) and mereology (the h:partOf hierarchy). Other important relationship types, such as peer-to-peer, dependency, or hierarchical supervision, are considered domain-specific and are intentionally excluded from this core vocabulary.

This design follows the principle of minimality. RDF-H provides the universal, structural primitives for building holarchies. Modelers are encouraged to define their own domain-specific properties (e.g., ex:isPeerOf, ex:dependsOn) in their own ontologies. The RDF-H pattern is then used to place these custom relationships within the context of a holon. This approach promotes a more flexible and composable ecosystem, where the core RDF-H pattern can be applied to any relationship, without the RDF-H vocabulary itself becoming an exhaustive and overly prescriptive ontology.

Example of using a domain-specific property with RDF-H:

@prefix ex:  <http://example.org/network#> .
@prefix h:   <https://w3id.org/rdf-h#> .
@prefix owl: <http://www.w3.org/2002/07/owl#> .

# A domain-specific property defined in an external ontology
ex:isPeerOf a owl:ObjectProperty, owl:SymmetricProperty .

# The holon resource. Explicit typing is RECOMMENDED for portability,
# even though h:inHolon's range axiom would entail it under RDFS.
ex:SystemCluster a h:Holon .

# Applying the RDF-H pattern to the domain-specific property
@holon ex:SystemCluster {
    ex:ServiceA ex:isPeerOf ex:ServiceB .
}

Formal Semantics and Entailment

The semantics of RDF-H are defined by the standard RDF 1.2 model-theoretic semantics [[RDF12-SEMANTICS]] applied to graphs containing the RDF-H vocabulary. No new entailment regime is required; rather, standard RDFS or OWL reasoners will produce the desired inferences based on the ontology.

Holon Inference

The primary inference in RDF-H is the typing of a resource as a h:Holon. This is achieved via the rdfs:range axiom on the h:inHolon property.

Ontology Axiom (Turtle):

@prefix h: <https://w3id.org/rdf-h#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .

h:inHolon rdfs:range h:Holon .

Entailment Rule (h-holon-type):

IF:   ?r h:inHolon ?c .
THEN: ?c rdf:type h:Holon .

This rule means that any resource appearing as the object of an h:inHolon triple is inferred to be an instance of h:Holon. The subject ?r is a reifier — an IRI or blank node that, in the RDF 1.2 reifies model, identifies a particular occurrence of an asserted triple.

Because this typing is only an entailment, it may not be visible to consumers that do not apply RDFS reasoning. The h:HolonIntegrityConstraintComponent defined in surfaces holons whose typing relies on this entailment, and modelers SHOULD declare h:Holon explicitly for portability.

Part-Whole Inference

Queries for the general h:partOf property will entail results from all its sub-properties.

Data:

ex:Engine h:componentOf ex:Car .
ex:Player h:memberOf ex:Team .

Query:

SELECT ?part ?whole WHERE { ?part h:partOf ?whole . }

An RDFS-aware reasoner will return both the engine-car and player-team pairs, because it knows that h:componentOf and h:memberOf are sub-properties of h:partOf.

Acyclicity and Well-Foundedness

The requirement that part-whole hierarchies be acyclic is a fundamental guarantee of the logical soundness of any compositional model — analogous to the Axiom of Foundation in Zermelo–Fraenkel set theory [[SEP-SELFREF]]. The normative MUST-NOT statement of this requirement appears in ; the OWL- and SHACL-level enforcement mechanisms are described in and respectively.

Turtle-H: A Syntactic Sugar for Turtle

Future direction. Turtle-H — the @holon directive defined in this section — is logically separable from the rest of RDF-H: it is a Turtle 1.2 surface-syntax extension whose only specified semantics is its desugaring (see the desugaring rules below). A future revision MAY extract Turtle-H into a standalone companion specification — for example, a "Turtle-H Surface Syntax" document that the core RDF-H specification merely references — or, if the Turtle 1.2 Working Group finds the construct broadly useful, MAY propose its integration into a future revision of Turtle itself. The @holon token, the EBNF productions in , and the desugaring rules are intended to remain stable across either path. Community feedback is invited (see Open Issue 6).

To simplify the authoring of holonic structures, this specification proposes Turtle-H, a syntactic sugar for Turtle that introduces a directive-led block syntax for defining a holon's context. A conformant RDF-H processor SHOULD support this syntax.

The @holon Directive

A holon and its constituent relationships are defined by the @holon directive, followed by the holon's identifier (IRI or blank node) and a block of Turtle statements enclosed in curly braces: 

@holon <holon-iri> {
    # Turtle statements that are constituents of this holon
}

Why a directive (and not a bare IRI { ... } block)? The bare-brace form <iri> { ... } already has a defined meaning in TriG [[TRIG]], where it denotes a named graph. Reusing that surface syntax for an unrelated semantics (holonic context) would silently misparse Turtle-H input under any TriG-aware parser, and vice versa. The @holon keyword makes Turtle-H grammatically distinct from TriG and unambiguous to a single parser pass.

Turtle-H is not part of the standard Turtle 1.2 specification [[RDF12-TURTLE]]. It is a proposed syntactic sugar for RDF-H. In standard Turtle 1.2 a developer must write two separate constructs — the asserted triple, and an annotation block (or a separate reifier triple) linking it to the holon. The @holon block lets the developer write the relationship once; a Turtle-H-aware parser generates both required triples.

Example using Turtle-H Syntax:

@prefix ex: <http://example.org/> .
@prefix h: <https://w3id.org/rdf-h#> .

ex:Car_123 a h:Holon .
ex:Engine_456 a h:Holon .

@holon ex:Car_123 {
    ex:Engine_456 h:componentOf ex:Car_123 .

    @holon ex:Engine_456 {
        ex:Piston_789 h:componentOf ex:Engine_456 .
    }
}

This concise syntax is syntactic sugar for the standard RDF 1.2 representation. A Turtle-H parser MUST translate the block syntax into the equivalent set of standard triples.

The block @holon :H { :s :p :o . } desugars per Turtle-H into:

  1. The Base Fact: The relationship itself is asserted.
    :s :p :o .
  2. The Context Fact: The relationship's reifier is linked to its containing holon.
    << :s :p :o >> h:inHolon :H .

The reified-triple form << :s :p :o >> is itself sugar in Turtle 1.2 [[RDF12-TURTLE]] — it allocates a fresh blank-node reifier related to the triple term <<( :s :p :o )>> via rdf:reifies. The fully-expanded RDF 1.2 form is therefore three triples per @holon-enclosed statement, as shown below.

RDF 1.2 Equivalent of the Turtle-H Example (using reified-triple sugar):

@prefix ex: <http://example.org/> .
@prefix h: <https://w3id.org/rdf-h#> .

ex:Car_123 a h:Holon .
ex:Engine_456 a h:Holon .

# Triples generated from the ex:Car_123 context
ex:Engine_456 h:componentOf ex:Car_123 .
<< ex:Engine_456 h:componentOf ex:Car_123 >> h:inHolon ex:Car_123 .

# Triples generated from the nested ex:Engine_456 context
ex:Piston_789 h:componentOf ex:Engine_456 .
<< ex:Piston_789 h:componentOf ex:Engine_456 >> h:inHolon ex:Engine_456 .

Fully-expanded RDF 1.2 form (no syntactic sugar):

@prefix ex:  <http://example.org/> .
@prefix h:   <https://w3id.org/rdf-h#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .

ex:Car_123    a h:Holon .
ex:Engine_456 a h:Holon .

ex:Engine_456 h:componentOf ex:Car_123 .
_:r1 rdf:reifies <<( ex:Engine_456 h:componentOf ex:Car_123 )>> .
_:r1 h:inHolon ex:Car_123 .

ex:Piston_789 h:componentOf ex:Engine_456 .
_:r2 rdf:reifies <<( ex:Piston_789 h:componentOf ex:Engine_456 )>> .
_:r2 h:inHolon ex:Engine_456 .

This syntactic sugar improves readability and writability while remaining fully compatible with the standard RDF 1.2 data model.

Assertion Semantics: Reifiers, Triple Terms, and Asserted Triples

RDF 1.2 distinguishes three things that are easy to conflate [[RDF12-CONCEPTS]]:

  • An asserted triple :s :p :o . claims that the relationship holds.
  • A triple term <<( :s :p :o )>> is an RDF term that denotes the triple (:s, :p, :o); in RDF 1.2 a triple term may appear only as the object of another triple, never as a subject.
  • A reifier is an IRI or blank node that is related to a triple term via rdf:reifies; the reifier identifies a particular occurrence of the underlying triple and is itself an ordinary RDF resource that may appear as either subject or object.

In Turtle 1.2 [[RDF12-TURTLE]] the bare-brace form << :s :p :o >> is syntactic sugar for a fresh blank-node reifier together with the rdf:reifies triple that ties it to the underlying triple term. Concretely, << :s :p :o >> h:inHolon :H . expands to _:b rdf:reifies <<( :s :p :o )>> . _:b h:inHolon :H . Asserting this does not by itself assert :s :p :o — it only asserts that a reifier of that triple is in holon :H.

RDF-H therefore imposes the following normative requirement:

  • For every reifier ?r with ?r h:inHolon :H in a conformant RDF-H graph, if ?r rdf:reifies <<( :s :p :o )>> holds, then the base triple :s :p :o MUST also be asserted in the same graph.
  • The @holon directive of Turtle-H satisfies this requirement automatically by emitting both the asserted triple and the reifier-with-h:inHolon on desugaring (see the desugaring rules).

"Being in a holon" is therefore an annotation on a relationship that is already claimed to hold; it never substitutes for the assertion itself.

This requirement is necessary because RDF 1.2 Semantics [[RDF12-SEMANTICS]] places no truth-preserving constraint on rdf:reifies: asserting that a reifier reifies a triple term carries no model-theoretic commitment to the truth of the underlying triple. Without the explicit RDF-H rule above, an RDF-H graph could legitimately contain ?r h:inHolon :H for a reifier of a triple that is not itself asserted, which would make holons unsound containers for the relationships they purport to gather. RDF 1.2 Semantics likewise places no identity constraint on reifiers of the same triple term, which is what enables the multiple-holons-per-triple pattern shown below.

Equivalent forms

Because << ... >> h:inHolon :H reduces to a reifier carrying h:inHolon :H, it is equivalent to using the standard Turtle 1.2 annotation syntax {| h:inHolon :H |} directly:

The following three Turtle 1.2 fragments are all equivalent in RDF 1.2:

# (a) Annotation syntax — most idiomatic in Turtle 1.2
ex:Engine_456 h:componentOf ex:Car_123 {| h:inHolon ex:Car_123 |} .

# (b) Reified-triple sugar — what Turtle-H @holon desugars to
ex:Engine_456 h:componentOf ex:Car_123 .
<< ex:Engine_456 h:componentOf ex:Car_123 >> h:inHolon ex:Car_123 .

# (c) Fully expanded — no syntactic sugar
ex:Engine_456 h:componentOf ex:Car_123 .
_:b rdf:reifies <<( ex:Engine_456 h:componentOf ex:Car_123 )>> .
_:b h:inHolon ex:Car_123 .

The same triple in multiple holons

A single base triple MAY appear in more than one holon. Each additional containing holon is recorded by an additional reifier carrying its own h:inHolon. There is no implicit relationship between the holons that share a triple. 

@prefix ex: <http://example.org/> .
@prefix h: <https://w3id.org/rdf-h#> .

ex:Engine_456 h:componentOf ex:Car_123
    {| h:inHolon ex:Car_123 |}
    {| h:inHolon ex:DriveTrain_789 |} .

Distinction from named graphs

A holon is a resource within a graph; an RDF-H graph is a single, unified RDF 1.2 graph in which holonic structure is encoded by reifiers carrying h:inHolon triples. This is fundamentally different from a TriG named graph [[TRIG]], which partitions a dataset into separately addressable graphs. A Turtle-H processor MUST NOT treat an @holon block as a named graph, and a TriG processor MUST NOT treat a TriG <iri> { ... } block as a holon block.

Querying Holonic Graphs with SPARQL

Querying RDF-H graphs does not require any extension to SPARQL. All holonic structures can be queried using standard SPARQL 1.1 [[SPARQL11-QUERY]] together with the SPARQL 1.2 reified-triple patterns and triple-term syntax that accompany the RDF 1.2 reifier model [[RDF12-CONCEPTS]].

Querying Holonic Context

The core pattern for querying within a holon's context involves finding the reifiers linked to it via h:inHolon, and matching the triple they reify. The SPARQL 1.2 reified-triple pattern << ?s ?p ?o >> matches any reifier of a triple with that shape, so it composes directly with h:inHolon.

Example Query: Find all component relationships defined within the context of ex:Engine_456.

PREFIX ex: <http://example.org/>
PREFIX h:  <https://w3id.org/rdf-h#>

SELECT ?part ?engine
WHERE {
    << ?part h:componentOf ?engine >> h:inHolon ex:Engine_456 .
}

Equivalently, the fully-expanded RDF 1.2 form makes the reifier explicit:

PREFIX ex:  <http://example.org/>
PREFIX h:   <https://w3id.org/rdf-h#>
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>

SELECT ?part ?engine
WHERE {
    ?r rdf:reifies <<( ?part h:componentOf ?engine )>> .
    ?r h:inHolon ex:Engine_456 .
}

Querying Across the Part-Of Hierarchy

Standard property paths can be used to query for specific or general part-whole relationships.

Example Query: Find all components, direct and indirect, of ex:Car_123.

PREFIX ex: <http://example.org/>
PREFIX h:  <https://w3id.org/rdf-h#>

# This query uses a property path on the specific 'componentOf' relation.
SELECT ?component
WHERE {
  ?component h:componentOf+ ex:Car_123 .
}

Example Query: Find all parts of ex:Car_123, regardless of the specific relationship type (component, member, etc.).

PREFIX ex: <http://example.org/>
PREFIX h:  <https://w3id.org/rdf-h#>

# This query uses the general 'partOf' relation. An RDFS-aware engine will
# traverse across all its sub-properties.
SELECT ?part
WHERE {
  ?part h:partOf+ ex:Car_123 .
}

Validation with SHACL

The Shapes Constraint Language (SHACL) [[SHACL]] is the standard mechanism for validating RDF graphs. To facilitate the validation of holonic graphs, the RDF-H vocabulary includes two built-in Constraint Components. These components encapsulate the core structural integrity rules of the RDF-H pattern, making it simpler to write robust and reusable SHACL shapes. A conformant RDF-H processor that performs SHACL validation SHOULD recognize and implement these components.

Built-in Constraint Component: AcyclicPartConstraintComponent

This component validates the most critical structural rule: that the part-whole hierarchy must be acyclic. A holon cannot be a part of itself, either directly or indirectly.

  • IRI: h:AcyclicPartConstraintComponent
  • Constraint: A focus node violates this constraint if there exists a non-empty property path of h:partOf from the focus node back to itself.

Example SHACL Shape using the component:

ex:AcyclicPartShape
    a sh:NodeShape ;
    sh:targetClass h:Holon ;
    sh:constraint [
        a h:AcyclicPartConstraintComponent ;
        sh:message "The holon participates in a part-of cycle." ;
    ] .

Formal Definition of the Validator:

h:AcyclicPartConstraintComponent a sh:ConstraintComponent ;
    sh:validator h:AcyclicPartValidator .

h:AcyclicPartValidator a sh:SPARQLValidator ;
    sh:message "The focus node participates in a part-of cycle."@en ;
    sh:select """
        PREFIX h: 
        SELECT $this
        WHERE {
            $this (h:partOf|h:directlyPartOf|h:componentOf|h:memberOf|h:substanceOf|h:portionOf)+ $this .
        }
    """ .

The validator alternates explicitly over h:partOf and its declared sub-properties because SPARQL property paths do not traverse rdfs:subPropertyOf without RDFS entailment. Under a SHACL engine that applies RDFS entailment [[SPARQL11-ENTAILMENT]], the simpler form $this h:partOf+ $this is equivalent.

Built-in Constraint Component: HolonIntegrityConstraintComponent

This component validates that any resource acting as a holon (i.e., as the object of an h:inHolon property) is explicitly declared to be of type h:Holon.

Because h:inHolon declares rdfs:range h:Holon, any RDFS-aware processor will infer the h:Holon type for every object of h:inHolon; under such an engine the constraint is trivially satisfied. The component therefore acts as a portability / quality check: it surfaces holons whose typing relies on entailment and that would consequently appear untyped to a non-inferring consumer. Modelers SHOULD declare h:Holon explicitly for every holon.

  • IRI: h:HolonIntegrityConstraintComponent
  • Constraint: Under a non-inferring SHACL engine, a focus node violates this constraint if it is the object of an h:inHolon triple but is not explicitly declared as an rdf:type of h:Holon.

Example SHACL Shape using the component:

ex:HolonIntegrityShape
    a sh:NodeShape ;
    sh:targetObjectsOf h:inHolon ;
    sh:constraint [
        a h:HolonIntegrityConstraintComponent ;
        sh:message "This resource is used as a holon but is not typed as h:Holon." ;
    ] .

Formal Definition of the Validator:

h:HolonIntegrityConstraintComponent a sh:ConstraintComponent ;
    sh:validator h:HolonIntegrityValidator .

h:HolonIntegrityValidator a sh:SPARQLValidator ;
    sh:message "The focus node is used as a holon (object of h:inHolon) but is not explicitly typed as h:Holon."@en ;
    sh:select """
        PREFIX h: 
        SELECT $this
        WHERE {
            ?s h:inHolon $this .
            FILTER NOT EXISTS { $this a h:Holon . }
        }
    """ .

Worked Example: Smart Building Digital Twin

This section presents a realistic, end-to-end RDF-H example: a digital twin of a single floor of an office building, including its HVAC subsystem, occupants, and material composition. The example exercises every part-of sub-property (h:componentOf, h:memberOf, h:substanceOf, h:portionOf), nested holons, domain-specific predicates within a holon's context, SPARQL queries against the resulting graph, and SHACL validation.

The example uses two namespace prefixes in addition to the RDF-H prefix: bldg: for building-domain vocabulary defined in an external ontology, and ex: for the instance data.

The Data

Turtle-H source:

@prefix bldg: <https://example.org/bldg#> .
@prefix ex:   <https://example.org/twin/> .
@prefix h:    <https://w3id.org/rdf-h#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .
@prefix xsd:  <http://www.w3.org/2001/XMLSchema#> .

# --- Domain-specific vocabulary (external ontology) ---
bldg:monitors        a owl:ObjectProperty .
bldg:occupies        a owl:ObjectProperty .
bldg:cooledBy        a owl:ObjectProperty .

# --- Holon declarations (explicit typing recommended for portability) ---
ex:Building_A         a h:Holon ; bldg:address "1 Market St, San Francisco, CA" .
ex:Floor_3            a h:Holon .
ex:HVAC_F3            a h:Holon .
ex:Compressor_F3      a h:Holon .
ex:Room_301           a h:Holon .

# --- Top-level holon: the building, with its floors and tenant ---
@holon ex:Building_A {
    ex:Floor_3        h:componentOf ex:Building_A .
    ex:Floor_4        h:componentOf ex:Building_A .
    ex:Tenant_Acme    h:memberOf    ex:Building_A .
    ex:AnnualEnergy_2026 h:portionOf ex:Building_A_EnergyHistory .
}

# --- Floor 3, with its rooms and shared HVAC subsystem ---
@holon ex:Floor_3 {
    ex:Room_301       h:componentOf ex:Floor_3 .
    ex:Room_302       h:componentOf ex:Floor_3 .
    ex:HVAC_F3        h:componentOf ex:Floor_3 .

    # A domain-specific relationship placed within the floor's holonic context
    ex:Room_301       bldg:cooledBy ex:HVAC_F3 .
    ex:Room_302       bldg:cooledBy ex:HVAC_F3 .
}

# --- Room 301: occupants and the wall material ---
@holon ex:Room_301 {
    ex:Person_Smith   bldg:occupies ex:Room_301 .
    ex:Person_Jones   bldg:occupies ex:Room_301 .
    ex:Concrete_Mix_C30 h:substanceOf ex:Room_301_NorthWall .
}

# --- HVAC subsystem: components and a domain-specific monitoring relation ---
@holon ex:HVAC_F3 {
    ex:Compressor_F3  h:componentOf ex:HVAC_F3 .
    ex:DuctNetwork_F3 h:componentOf ex:HVAC_F3 .
    ex:TempSensor_F3  bldg:monitors ex:HVAC_F3 .
}

# --- Compressor: refrigerant is substance, transitive via h:partOf ---
@holon ex:Compressor_F3 {
    ex:Refrigerant_R410A h:substanceOf ex:Compressor_F3 .
}

After the Turtle-H parser desugars the @holon directives, the resulting graph contains the original assertions plus, for each statement enclosed in a holon block, an h:inHolon annotation on its reifier. For instance, the line ex:Room_301 bldg:cooledBy ex:HVAC_F3 . inside @holon ex:Floor_3 expands to that asserted triple plus << ex:Room_301 bldg:cooledBy ex:HVAC_F3 >> h:inHolon ex:Floor_3 . (which itself further expands to a fresh blank-node reifier with rdf:reifies — see the desugaring rules).

Querying the Graph

The following queries illustrate the kinds of questions the holonic structure makes straightforward to answer.

Query 1: List every part of ex:Building_A, at any depth, regardless of part-of sub-type. RDFS-aware engines traverse all sub-properties of h:partOf.

PREFIX ex: <https://example.org/twin/>
PREFIX h:  <https://w3id.org/rdf-h#>

SELECT DISTINCT ?part WHERE {
    ?part h:partOf+ ex:Building_A .
}

Expected results (under RDFS entailment): ex:Floor_3, ex:Floor_4, ex:Tenant_Acme, ex:AnnualEnergy_2026, ex:Room_301, ex:Room_302, ex:HVAC_F3, ex:Compressor_F3, ex:DuctNetwork_F3, ex:Refrigerant_R410A.

Query 2: What relationships are scoped to the floor's holonic context? This finds every triple-occurrence whose reifier is h:inHolon ex:Floor_3. 

PREFIX ex: <https://example.org/twin/>
PREFIX h:  <https://w3id.org/rdf-h#>

SELECT ?s ?p ?o WHERE {
    << ?s ?p ?o >> h:inHolon ex:Floor_3 .
}

Returns the five statements asserted inside @holon ex:Floor_3: the three h:componentOf triples and the two bldg:cooledBy triples. Crucially, the same bldg:cooledBy assertions made elsewhere (e.g., inside another building's floor holon) would not be returned, even if the triples themselves were structurally identical, because each assertion has its own reifier.

Query 3: Find every temperature sensor that monitors an HVAC subsystem somewhere in ex:Building_A, joining a domain-specific relationship with the holonic structure.

PREFIX bldg: <https://example.org/bldg#>
PREFIX ex:   <https://example.org/twin/>
PREFIX h:    <https://w3id.org/rdf-h#>

SELECT ?sensor ?hvac WHERE {
    ?sensor bldg:monitors ?hvac .
    ?hvac   h:partOf+      ex:Building_A .
}

Returns (ex:TempSensor_F3, ex:HVAC_F3). Note that the query does not need to mention floors, rooms, or the holonic structure explicitly; the transitive h:partOf+ traversal does the work.

Validation

Applying the SHACL shapes from to the example graph produces no violations — the part-of hierarchy is acyclic, and every holon used as the object of h:inHolon is explicitly typed as h:Holon.

To illustrate detection, consider the following invalid addition to the graph: 

# A bug: the building is mistakenly declared a component of one of its own floors.
ex:Building_A h:componentOf ex:Floor_3 .

With this triple added, the h:AcyclicPartConstraintComponent reports a violation on ex:Building_A: there now exists a part-of cycle ex:Building_A → ex:Floor_3 → ex:Building_A via the alternation over h:componentOf and the transitive closure under h:partOf. An OWL DL reasoner would also flag the graph as inconsistent, since h:componentOf is declared owl:AsymmetricProperty and the two h:componentOf triples contradict each other.

Appendix A: Turtle-H Grammar

This appendix specifies the additional grammar productions that Turtle-H introduces over Turtle 1.2 [[RDF12-TURTLE]]. The notation follows the EBNF style used by the Turtle 1.2 specification. Production names that appear in italics (e.g., iri, BlankNode, triples) refer to the corresponding productions in Turtle 1.2 and are not redefined here.

A Turtle-H document is a Turtle 1.2 document extended with the @holon directive. Concretely, the statement production of Turtle 1.2 is extended with one additional alternative: 

[H1]   statement       ::=  directive | triples '.' | holonBlock

[H2]   holonBlock     ::=  '@holon' holonId '{' holonContent* '}'

[H3]   holonId        ::=  iri | BlankNode

[H4]   holonContent   ::=  triples '.' | holonBlock

Whitespace and comments are permitted between any two tokens, as in Turtle 1.2. The @holon keyword is case-sensitive.

Desugaring (informative). A parser that accepts Turtle-H MUST translate each holonBlock into the equivalent Turtle 1.2 triples described in the desugaring rules. For each holonContent that is itself a triples '.' production with subject :s, predicate :p and object :o, and for the enclosing holonId :H, the parser emits: 

:s :p :o .
<< :s :p :o >> h:inHolon :H .

For predicate-object lists (multiple objects per subject) and object lists (multiple p o pairs per subject) the parser emits one h:inHolon annotation per generated triple. Nested holonBlocks desugar recursively, with each nested block producing h:inHolon annotations against its own enclosing holonId rather than the outer one.

Disambiguation from TriG. The holonBlock production starts unambiguously with the keyword @holon, which is not a valid token at the same grammatical position in either Turtle 1.2 or TriG [[TRIG]]. A parser MUST NOT treat a TriG named-graph block (iri '{' triples '}') as a holonBlock, and vice versa.

Appendix B: Open Issues

The editors invite community feedback on the following design questions. Each is intended to be resolved before a v1.0 milestone of this specification.

Issue 1: Extraction of the mereology vocabulary
As noted in , the h:partOf hierarchy is logically separable from the holon machinery and may be extracted into a standalone vocabulary at a sibling namespace. Feedback is sought on (a) whether the extraction should happen, (b) the preferred sibling namespace (e.g., https://w3id.org/rdf-mereo#), and (c) whether the extracted vocabulary should also publish migration guidance for graphs authored against the bundled v0.x form.
Issue 2: Status of the w3id.org namespace redirect
The vocabulary IRI https://w3id.org/rdf-h# requires a redirect entry in the perma-id/w3id.org registry before any published consumer can dereference it. Until that redirect is in place, citations to RDF-H IRIs are not resolvable on the open web.
Issue 3: OWL profile choice
Option (c) was selected for the part-of hierarchy (split h:partOf / h:directlyPartOf) to keep the vocabulary in OWL DL. Feedback is sought on whether OWL DL conformance is the right target — alternatives include (a) accepting OWL Full and declaring all part-of properties transitive + asymmetric + irreflexive on a single property, or (b) dropping asymmetry/irreflexivity from OWL entirely and relying on SHACL alone.
Issue 4: Empty and singleton holons
The current vocabulary permits a resource to be typed as h:Holon without any h:inHolon-linked relationships. Should the spec require non-emptiness of holons, or is the permissive interpretation correct? The current draft favors permissiveness on the grounds that empty holons may legitimately be created in anticipation of future content.
Issue 5: Closed-world holon contents
There is currently no way to assert "these triples — and only these triples — are in holon :H." Should the spec define a closure mechanism (e.g., a h:closed annotation, or a SHACL-based pattern), or is the open-world interpretation sufficient?
Issue 6: Turtle-H normative status and venue
Turtle-H is currently bundled into this document as a SHOULD-level optional syntactic sugar. Three independent questions are open for community feedback:
  1. Normative level. Should Turtle-H remain SHOULD-level optional, or be promoted to MUST-level required syntax for a conformant RDF-H processor?
  2. Document venue. Should Turtle-H stay bundled in this specification, or be extracted into a standalone companion document ("Turtle-H Surface Syntax") that the core RDF-H specification merely references? Extraction would parallel the proposed treatment of the mereology vocabulary (see Open Issue 1).
  3. Upstream integration. Should the editors propose the @holon directive — or a generalization of it — to the Turtle Working Group for integration into a future revision of Turtle 1.2 itself? The construct is RDF-H-specific in its desugaring (it emits an h:inHolon annotation), but a generalized form (e.g., a per-block annotation directive parameterized by an arbitrary predicate) might be of broader interest to the Turtle community.

Appendix C: Security and Privacy Considerations

RDF-H introduces no new security or privacy considerations beyond those of the underlying specifications it depends on ([[RDF12-CONCEPTS]], [[RDF12-SEMANTICS]], [[RDF12-TURTLE]], [[SPARQL11-QUERY]], [[SHACL]]). Implementers and consumers of RDF-H graphs should however be aware of the following:

  • Triple-occurrence leakage. Because h:inHolon annotations identify occurrences of triples (via reifiers), an RDF-H graph may carry more identifying or contextual information about a triple than a flat RDF graph would. When merging or publishing RDF-H graphs that originated from access-controlled subgraphs, publishers SHOULD review which holons are exposed and whether the resulting triple-occurrence metadata constitutes an information leak.
  • Cycle-checking cost. The acyclicity validator described in evaluates a transitive property path over potentially large graphs. Engines processing untrusted input SHOULD apply standard resource limits to bound query evaluation cost.
  • Reifier identity. Reifiers that are blank nodes (the default form produced by the Turtle 1.2 reified-triple sugar and by the @holon directive) are not stable across graph serializations. Applications that rely on reifier identity across exchanges SHOULD use IRI reifiers explicitly.

Conclusion

This specification introduces RDF-H, a powerful and flexible modeling pattern for representing compositional structures in RDF. By building directly on the RDF 1.2 reifier model and triple terms, it provides a semantically sound and structurally intuitive method for modeling "wholes-within-wholes." The core vocabulary, centered on h:inHolon and a formal mereological hierarchy, is both simple and expressive. The proposed Turtle-H syntactic sugar makes the pattern highly accessible to developers, bridging the gap between the intuitive feel of property graphs and the formal rigor of RDF. RDF-H provides a robust, standards-based foundation for the next generation of knowledge graphs in domains such as digital twins, systems engineering, contextual AI, and the Spatial Web.
