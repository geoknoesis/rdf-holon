RDF-H organizes RDF statements into identifiable units called holons. Each holon has explicitly assigned content. Optional parent links organize holons; optional imports select additional content for queries. RDF-H provides two ways to store this organization, explained below.

This document is the frozen snapshot of RDF-H 0.8, released on 2026-10-21 (repository tag rdf-h-v0.8.0) and identified by https://w3id.org/rdf-h/0.8. The vocabulary of this release is rdfh.ttl. The editor's draft may be newer.

This is the RDF-H 0.8 community draft, produced by Geoknoesis LLC. It is not a W3C specification. Feedback is welcome in the repository. The specification, vocabulary, and examples use the Apache 2.0 license.

Introduction

RDF-H organizes RDF statements into identifiable content units. A holon can stand alone or be organized under another holon using a parent hierarchy.

RDF-H addresses recurring needs that plain RDF graphs and datasets leave to convention:

  • Decomposing a description. A large description (a building, a regulation, a product) is authored and maintained as units that can be queried alone or together, without duplicating statements.
  • Keeping several descriptions of one resource apart. Independent sources, revisions, or viewpoints file their own statements about the same subject; the reifier profile records which occurrence came from where.
  • Explicit read scope. An application asks for exactly a unit, a unit with everything organized under it, or that plus explicitly imported units, and receives one graph, or a dataset in which each unit's statements remain attributed to it.
  • Unit-specific validation. Each unit selects the shapes that apply to it, so one dataset can hold units validated under different rules.
  • A stable registry. Which units exist, where their content lives, and how they are organized is stated in one metadata context, not inferred from the data.

Three design decisions follow from these needs. Filing a statement never changes whether it is asserted (the additive invariant), so RDF-H data remains ordinary RDF for every consumer. All organization is explicit in the metadata context M; no entailment creates, moves, or hides content. And both storage profiles use only standard RDF 1.1 datasets or RDF 1.2 reifiers, so no new serialization is required to use RDF-H.

Terms Used in This Specification

This specification assumes basic RDF knowledge. The following terms explain how RDF-H uses RDF.

  • An RDF statement, also called a triple, has a subject, predicate, and object. To assert a statement is to include it as a claim in the data. Assertion does not establish that the claim is true.
  • An RDF graph is a set of triples: repeated copies of the same triple count once. A dataset contains one default graph and zero or more named graphs. A named graph has an identifier that lets queries select it.
  • An IRI is an identifier such as https://example.org/City. A blank node identifies a resource without giving it an IRI. Labels such as _:city identify blank nodes within their source; matching labels in separate sources do not imply the same resource.
  • To file a statement in a holon means to assign it to that holon's content. This assignment is called membership. Filing does not move the statement out of the asserted data.
  • A representation, also called a profile here, is a way to store holons and their memberships. The dataset profile stores each holon's content in a named graph. The reifier profile records memberships using RDF resources that refer to statements.
  • A triple term is an RDF 1.2 term that represents a subject, predicate, and object triple without asserting it. A reifier is an IRI or blank node linked to a triple term by rdf:reifies. It can carry membership and other information about that occurrence of the statement. An occurrence is one such separately identified record; several occurrences may refer to the same triple.
  • A parent link places one holon directly under another for organization. Following parent links upward reaches ancestors; following them downward reaches descendants. An import explicitly selects another holon's direct content.
  • A query's scope is the content selected for it. Direct scope selects one holon's own content. Aggregated scope adds its descendants' content. Visible scope also adds the direct content of holons imported by the selected holon. Global scope, used only by validation and reasoning requests, is all asserted data G.
  • A holonic graph is RDF data organized into holons: a body of RDF with its metadata context M. The conformance class RDF-H Graph states its requirements.

The notation uses H for a selected holon, M for the metadata graph that controls RDF-H processing, and G for all asserted RDF-H data. Metadata means information used to manage the holons, rather than just describe their subject matter. CG(H) names H's direct content. The processing rules below define exactly what belongs to each graph.

A shape is a set of validation requirements. A shapes graph stores those requirements as RDF statements. Shapes are separate from the content they validate.

A Holon in One Example

The default graph identifies two holons. Each named graph contains the statements filed in its holon.

@prefix h: <https://w3id.org/rdf-h#> .
@prefix ex: <https://example.org/> .

ex:Building a h:Holon .
ex:Floor a h:Holon .

ex:Building { ex:Building ex:name "Library" . }
ex:Floor { ex:Floor ex:level 1 . }

The building's content is its name statement; the floor's content is its level statement. Both statements are asserted under RDF-H's dataset interpretation. Neither holon needs a parent. To organize the floor holon under the building holon, add ex:Floor h:parentHolon ex:Building to the default graph. This organizes descriptions; it does not assert physical parthood.

A hierarchy organizes holons through parent links. An explicit aggregated query reads a holon and its descendants; it does not read its ancestors. An import adds another holon's direct content without making it a parent or copying its content. Both features are optional; a plain named-graph query still reads only direct content.

The rule that filed statements are also asserted is called the additive invariant. Like any RDF assertion, a claim can be mistaken; RDF-H does not verify its truth.

Reading This Specification

Read the core model, then choose named graphs or reifiers. The processing algorithm is the normative statement of how holons are resolved and which errors arise. Add hierarchy and imports when organizing holons and validation when selecting shapes. Implementers should also read conformance and conversion; the design rationale explains the choices behind the model.

Conventions

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here. Examples and informative sections are explanatory; other sections define requirements. Optional capabilities apply only when claimed. The prefix h: denotes https://w3id.org/rdf-h#. An organized collection of holons may be called a holarchy.

Holon Identity

A holon identifier MAY also identify the domain resource being described. When a document, revision, or alternative description needs its own identity, applications SHOULD give it a separate holon identifier and an explicit application description relation.

owl:sameAs is the Web Ontology Language relation declaring that two identifiers refer to the same resource.

A content graph is the set of statements filed in a holon. The name of the graph storing that content does not change holon identity. Graph naming alone MUST NOT imply owl:sameAs between independently identified resources.

Content and Representations

Processing Context and Holon Registry

An RDF-H operation that looks up holons takes a data source and an explicitly designated metadata context M. M is an RDF graph containing the declarations that control processing: holon registrations, graph mappings, parent links, and imports. A registration makes a holon known to the processor. A graph mapping uses h:contentGraph to select the named graph containing its content. In the dataset profile, M defaults to the dataset's default graph. In the reifier profile, M MUST be supplied explicitly; it MAY be a separately supplied graph or an explicitly selected graph view, such as the document-level view a Turtle-H parser derives from top-level management statements. Processors MUST NOT silently treat all reifier data as M.

Blank nodes in M denote the same resources as blank nodes in the data only when both come from one blank-node scope: one document, one dataset, or a graph view of it. In the reifier profile, a membership can refer to a blank-node holon only when M is such a view, because a separately loaded M's labels do not denote the data's blank nodes. In the dataset profile, a blank-node holon with an IRI graph mapping works with any M, since the blank node is used only within M; a blank-node graph name, however, must share the dataset's scope.

The holon registry K(M) contains exactly the IRI or blank-node subjects in M explicitly typed h:Holon or the deprecated (retained for compatibility) h:CompleteHolon, or having an explicit h:contentGraph mapping. The registry uses only these explicit declarations, not facts inferred by a reasoning engine: inferring a type through RDF Schema (RDFS) does not register a holon, and a parent or import link registers neither holon it connects. Step 2 of the processing algorithm defines K(M) normatively.

The registry separates two cases that look alike in data: a holon outside K(M) is unknown and its selection is an error, while a registered holon with no filed content is known and empty. Memberships must refer to registered holons, and so must parent links and imports wherever a request checks them; the algorithm names the error for each case.

In the dataset profile, a holon's content is the named graph that its explicit h:contentGraph mapping selects, or, without a mapping, the graph named by the holon's own IRI. A blank-node holon therefore needs a mapping, and an absent graph simply means empty content. Graph names are not reserved per holon: several holons can select one graph, in which case their direct content is identical. Step 3 states these rules and their error conditions.

Unselected named graphs still contribute to G, but do not create registry entries. Default-graph statements are never dataset-profile content; they are filed only through reifier memberships in declared mixed data.

Management statements are the registrations, graph mappings, parent links, and imports listed above. When they appear only in content, they do not control RDF-H processing. M MAY intentionally contain a statement also filed as content, but converting representations MUST preserve M separately instead of promoting arbitrary content statements into declarations.

Direct Content and Assertion

In the notation below, H means the selected holon. A holon's content graph CG(H) is the set of triples explicitly filed in H. A holon may be empty; a statement may belong to several holons.

The asserted graph G is the union of the asserted source data and M: the supplied graph plus M in the reifier profile, or all default and named source graphs plus M in the dataset profile.

Every filed statement MUST also be in G: CG(H) ⊆ G. This is the additive invariant. Named-graph content satisfies it automatically; reifier-filed content requires an explicit base assertion.

The asserted union is an RDF-H interpretation, not a general RDF dataset rule. SPARQL default-graph queries do not automatically query that union [[RDF11-DATASETS]].

Named Graphs

In the dataset profile, a holon's selected named graph is its direct content. Holon declarations and graph mappings are in M, normally the default graph. The opening TriG example uses the holon IRI as the graph name [[TRIG]]. An explicit h:contentGraph mapping can select a different name.

Step 3 of the processing algorithm states how a holon's graph is selected. Reifiers offer an alternative when statement occurrences need independent identity or metadata.

RDF 1.2 Reifiers

A reifier is an IRI or blank node linked to a triple term by rdf:reifies. h:inHolon links the reifier to its containing holon [[RDF12-CONCEPTS]].

CG(H) contains exactly the triples reified by resources linked to H through h:inHolon. The example below uses the fully expanded form; Turtle 1.2 also supplies reifier and annotation shorthand [[RDF12-TURTLE]].

Assert the Base Statement

@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix h: <https://w3id.org/rdf-h#> .
@prefix ex: <https://example.org/> .

ex:Building a h:Holon .
ex:Building ex:name "Library" .
_:occurrence rdf:reifies <<( ex:Building ex:name "Library" )>> ;
    h:inHolon ex:Building .

For this example, designate M as the graph containing ex:Building a h:Holon. The data and M may share that assertion, but M is an explicit input; do not infer it from all data predicates. Turtle-H exposes the same metadata view automatically.

The name statement is asserted separately: neither rdf:reifies nor h:inHolon asserts it. This is how the reifier profile satisfies the additive invariant; a membership whose base statement is not asserted is the missing-base-assertion error of step 4.

Different reifiers MAY reify the same statement and carry different sources or occurrence metadata, including memberships in different holons. Direct content remains a set: repeated occurrences do not duplicate the triple.

Turtle-H Authoring

Turtle-H defines optional @holon blocks that emit assertions and membership annotations. Its expansion rules target the reifier profile. The grammar is maintained separately. Nesting blocks creates neither administrative parentage nor domain parthood.

Hierarchy and Declaration Validity

h:parentHolon is the immediate parent relation in M. A valid hierarchy is a forest: both ends of every parent link are registered holons, each child has at most one parent, and no chain of parent links returns to its starting holon. Several independent roots (holons with no parent) are permitted. Step 5 of the processing algorithm states these rules and their error conditions. The SPARQL property path h:parentHolon+ follows one or more parent links toward an ancestor. Reverse the direction to select descendants. This organizes content, not domain parthood.

Which checks a request performs depends on its scope. A direct request never depends on the hierarchy or imports, so an invalid parent link does not prevent reading one holon's content. Aggregated and visible requests depend on the whole parent relation, so an invalid link anywhere in M fails them, even outside the selected subtree. A visible request additionally checks only the selected holon's own imports. Registry and mapping errors anywhere in M fail every request to which those checks apply. This global validation deliberately couples otherwise separate subtrees: an unrelated invalid parent link can disable all aggregated and visible requests. Applications needing independent failure domains should supply separate authoritative metadata contexts. The processing algorithm states exactly which steps apply to which request.

Direct, Aggregated, and Visible Content

Choose the scope explicitly. A normal named-graph query reads only that graph; parent links and imports do not change SPARQL's graph selection.

All paths and imports in this section are read only from M. Descendants and import targets are registered holons; the data graphs themselves never supply management edges.

Query scopes
ScopeContent
Direct: CG(H)Only statements filed in H.
Aggregated: AG(H)Direct content of H and every descendant linked to H through one or more parent links.
Visible: VG(H)Aggregated content of H plus the direct content of holons explicitly imported by H.
Global: GAll asserted data, including M and unselected graphs. Available to validation and reasoning requests only; it is not a holon query scope and SPARQL-H does not offer it.

Step 7 of the processing algorithm defines these graphs normatively. In set notation, with D(H) = { K : K h:parentHolon+ H } and I(H) the direct targets of H's h:imports declarations:

AG(H) = CG(H) union all CG(K), for K in D(H)
VG(H) = AG(H) union all CG(I), for I in I(H)
  • Ancestors' content is excluded unless explicitly imported.
  • Descendant aggregation is recursive through parent links; each import adds only the named target's direct content; it does not follow further imports.
  • Only imports declared on H apply to VG(H). Imports declared by ancestors or descendants are not inherited.
  • An imported target contributes only its direct content, not its descendants, ancestors, or imports.
  • Self-import and cyclic imports are allowed because imports are not recursively expanded.
  • An import of an unregistered holon is an unresolved-import error, never silently empty content (step 6).

Combining scope graphs does not change which holon owns each membership. It also does not replace one conflicting assertion with another. Processors claiming composition support MUST implement aggregated and visible scope resolution, and SHOULD expose separate direct-content, aggregated-content, and visible-content operations. Visibility MUST NOT imply access authorization, local applicability, or a change in asserted truth. This is the only rule about what visibility grants; the validation and query sections additionally require disclosing any authorization filtering, and the security and privacy considerations explain the consequences.

Processing Algorithm and Error Conditions

This section is the normative statement of holon resolution: registration, graph mappings, memberships, hierarchy and import validity, and scope construction. The sections on the processing context, the hierarchy, and scopes explain these rules and their motivation; where their wording differs from this section, this section governs. Requirements that those sections state and this algorithm does not, such as how M is supplied, remain normative where they are stated.

The inputs are a data source S, a metadata context M, the declared profile, a selected holon H, and a scope: direct, aggregated, visible, or, for validation and reasoning requests only, global. S is an RDF dataset in the dataset profile and an RDF graph in the reifier profile. G is the union of M and all asserted triples in S (all default and named graphs for dataset or mixed input). M defaults to the default graph for dataset input; for reifier input it must be explicitly supplied. Blank nodes shared by S and M retain their identity only when they come from the same blank-node scope; independently loaded inputs are standardized apart.

  1. Profile selection. The operation request declares the profile. Absent a declaration, a dataset source uses the dataset profile and a graph source uses the reifier profile. Mixed data (both reifier memberships and named-graph content for one holon) MUST be declared by the request; without that declaration, reifier membership statements in a dataset-profile source are ordinary assertions and are not memberships. In the dataset profile the default graph is never a content graph. A reifier-profile request over a dataset designates one of its graphs as S; absent a designation, S is the dataset's default graph.
  2. Registry. K(M) is the set of IRI and blank-node subjects in M of rdf:type h:Holon, rdf:type h:CompleteHolon, or h:contentGraph, as explicitly stated in M. Nothing is added by entailment. If H is not in K(M), report unknown-holon.
  3. Mappings (dataset profile). For every K in K(M): if M states more than one distinct h:contentGraph value for K, report conflicting-mapping; if a value is neither an IRI nor a blank node (a literal or a triple term), report invalid-graph-name; if K is a blank node without a mapping, report unmapped-blank-node-holon. Otherwise the graph name of K is its mapping if present and K itself if K is an IRI. CG(K) is the named graph of S with that name, or the empty graph if S has no such graph. Several registered holons MAY share one graph name, through explicit mappings or because one holon's mapping names another holon's IRI; this is not an error, and a mapping target does not register a holon. In the reifier profile, h:contentGraph statements register holons but select no content unless mixed data is declared.
  4. Memberships (reifier profile). For every subject R of h:inHolon in S: each object MUST be in K(M), else report unregistered-membership-holon; R MUST have at least one rdf:reifies value, else report missing-reification; every such value MUST be a triple term, else report non-triple-term-reification; the triple denoted by every such term MUST be in G (an assertion in separately supplied M also satisfies this check), else report missing-base-assertion. CG(K) is the set of triples denoted by the triple terms of reifiers linked to K; a reifier linked to several holons files its triples in each.
  5. Hierarchy (aggregated and visible scopes only). For every statement C h:parentHolon P in M: C and P MUST be in K(M), else report unregistered-parent-endpoint; all parent statements for C MUST name the same P, else report multiple-parents; the relation MUST be acyclic, else report parent-cycle. D(H) is the set of holons reaching H by one or more parent links.
  6. Imports (visible scope only). For every statement H h:imports T in M, T MUST be in K(M), else report unresolved-import. I(H) is the set of such T. Imports declared by other holons are not checked and not used.
  7. Scope graph. Direct: CG(H). Aggregated: the union of CG(H) and CG(K) for K in D(H). Visible: the aggregated graph united with CG(T) for T in I(H). Global: G. Unions are set unions that preserve the blank-node identities of S. The selected holons of a request are H, the members of D(H) for aggregated and visible scope, and the members of I(H) for visible scope. On request a processor MAY return, instead of the scope graph alone, the attributed scope dataset: an RDF dataset whose default graph is the scope graph and which has one named graph per selected holon, named by the holon identifier and containing that holon's direct content. A blank-node holon names its graph with that blank node; holons that share a content graph yield distinct named graphs with equal content.
  8. Reporting. Return the scope graph, or the attributed scope dataset when requested, together with the identification of S or its snapshot, M, H, the scope, the profile, any filtering, and, for query and validation requests, the entailment regime. A processor that cannot perform a requested step because it lacks the capability reports unsupported-capability rather than a narrower scope; so does a request naming a scope this section does not define.

Step 2 applies to every request; step 3 applies in the dataset profile and step 4 in the reifier profile. For declared mixed data both apply, step 4 reads membership records from every graph of S, a base assertion may be in any graph of S or in M, and CG(K) is the union of the two results. In declared mixed data a blank-node holon without a mapping has empty named-graph content rather than raising unmapped-blank-node-holon, since its content may come from memberships alone. For global scope, H serves only to select the shapes of a validation request; a reasoning request need not name a holon, and step 2 is then skipped. Their checks cover all of M and S, not only the selected holon. Steps 5 and 6 apply as stated. Validation requests additionally report missing-shapes-graph when a graph named by h:importsShapes is absent from the validation dataset and ill-formed-shapes-graph when the effective shapes graph violates SHACL syntax rules. Because the checks depend only on M and S, processors MAY cache their outcome while M and S are unchanged.

Semantics and Reasoning

RDF-H uses standard RDF semantics [[RDF12-SEMANTICS]]. The range of h:inHolon entails holon typing under RDFS; the domains and ranges of the composition properties provide corresponding typing. Content extraction and visible-scope resolution are explicitly defined operations, not additional RDF entailment rules.

h:parentHolon is an immediate relation, not an OWL transitive property. Ancestors are selected with the property path h:parentHolon+. Neither a parent link nor content membership entails domain parthood.

Reasoning Scope

A reasoning operation MUST declare its input scope: direct CG(H), aggregated AG(H), or visible VG(H) when composition is supported, or global asserted G. It MUST declare its entailment regime and ontology inputs. Inferred statements MUST NOT be implicitly filed in a source holon.

A processor MAY return a separate derived graph or explicitly file derived assertions through an application update, preserving derivation provenance where available. Completeness declarations create no RDF or OWL negative entailments.

Separate Data and Shapes

Processors MUST identify the data dataset used to compute G. Every graph in it contributes to G, including metadata and unselected graphs. Being asserted does not automatically file a statement in a holon.

Shapes SHOULD be supplied separately as validation inputs, and derived graphs SHOULD be returned separately from asserted inputs. A graph present only in the shapes dataset is outside G and visible content. If shapes or derived graphs are deliberately included in the data dataset, their statements enter G; processors MUST NOT silently exclude them.

Querying the Three Scopes with Standard SPARQL

RDF-H does not require a SPARQL syntax extension. The three modes select the data to query, not a different query language. Standard property paths select holons, GRAPH reads their content, and CONSTRUCT combines it into one graph [[SPARQL11-QUERY]].

The optional experimental SPARQL-H companion provides FROM HOLON … SCOPE … shorthand for the same scope resolution. It requires a dedicated front end; the standard-SPARQL approach below remains fully supported.

Resolve the Scope, Then Run the Query

  1. Select the source data dataset, holon, and scope: direct, aggregated, or visible. A convenience API should default to direct and require an explicit request for wider scopes.
  2. Validate the selected holon registry, graph mappings, and mode-applicable hierarchy/import rules before building the scope. Apply the scope rules, including errors for unresolved imports.
  3. Resolve each selected holon's direct content and take the set union, preserving shared blank-node identity within the source dataset.
  4. Use the resolved graph as the query's default graph, then run ordinary SPARQL. Report the source dataset or snapshot, selected holon, scope, entailment regime, and any filtering alongside the results.

An example application request is query(holon=City, scope=aggregated, sparql=...). This illustrates an API convention; it is neither SPARQL syntax nor a new standard protocol parameter.

Build one graph before querying it. Wrapping an entire multi-pattern query in GRAPH ?g requires all those patterns to match the same named graph. It can miss joins between city statements and district statements. The resolved default graph permits those joins and deduplicates triples before counts and other aggregates are evaluated.

Build the Scope Graph

The following SPARQL 1.1 queries target the dataset profile. They assume a validated source dataset whose default graph is M and contains composition declarations and h:contentGraph mappings. Change ex:City to select another holon. Each query returns an RDF graph; run the application query against that result as a separate step.

These recipes assume registry and mode-specific checks have succeeded. When M is supplied externally, evaluate the declaration patterns against M (for example, construct a query view with M as its default graph) while retaining the source named content graphs. That query view does not change which source statements belong to G.

Direct Content

PREFIX h: <https://w3id.org/rdf-h#>
PREFIX ex: <https://example.org/>

CONSTRUCT { ?s ?p ?o }
WHERE {
    VALUES ?holon { ex:City }
    OPTIONAL { ?holon h:contentGraph ?declaredGraph }
    BIND(COALESCE(?declaredGraph, ?holon) AS ?graph)
    GRAPH ?graph { ?s ?p ?o }
}

    OPTIONAL { ?holon h:contentGraph ?declaredGraph }

Visible Content

PREFIX h: <https://w3id.org/rdf-h#>
PREFIX ex: <https://example.org/>

CONSTRUCT { ?s ?p ?o }
WHERE {
    { ?holon h:parentHolon* ex:City }
    UNION { ex:City h:imports ?holon }
    OPTIONAL { ?holon h:contentGraph ?declaredGraph }
    BIND(COALESCE(?declaredGraph, ?holon) AS ?graph)
    GRAPH ?graph { ?s ?p ?o }
}

COALESCE uses the explicit content-graph mapping when present and the holon IRI otherwise. A missing selected graph contributes empty direct content. These queries are scope construction recipes, not validators: a query alone will not diagnose an unresolved import or an invalid mapping.

For the reifier representation, use the same holon selection rules, extract CG(H) through rdf:reifies and h:inHolon with RDF 1.2-capable tooling, and build the same union graph. This does not require converting the query language or including reifier bookkeeping in the content result.

Default and Named Graphs

A scoped query service should expose the resolved graph as the default graph, with no named graphs unless the caller explicitly requests and is authorized for them. A caller that needs to know which holon each statement came from asks for the attributed scope dataset, whose named graphs are the selected holons' direct content; SPARQL-H requests it with FROM NAMED HOLONS. GRAPH ex:City must retain its standard meaning: it reads that named graph only if it is included in the query dataset. It must not silently mean aggregated or visible content. With a default-only query dataset, named-graph patterns have no matches.

Once a scope graph has a queryable IRI, an endpoint can expose it through standard FROM or SPARQL Protocol default-graph-uri dataset selection [[SPARQL11-QUERY]], [[SPARQL11-PROTOCOL]]. Neither mechanism computes descendant scope from a holon IRI automatically. Graph availability and IRI loading are endpoint-dependent. Do not assume several FROM clauses preserve shared blank nodes exactly as a union over the original dataset does; use a single resolved scope graph when that identity matters.

For a convenience scoped API, reject conflicting FROM, FROM NAMED, or protocol dataset selectors rather than silently changing the promised scope. A standard SPARQL endpoint continues to follow the standard query/protocol dataset-selection rules. Federated SERVICE calls explicitly query remote endpoints; a local scope is not an authorization boundary for those calls.

# Default graph: the aggregated scope graph, a deduplicated union.
ex:City ex:value "city" .
ex:District ex:value "district" .
ex:Neighborhood ex:value "neighborhood" .

# One named graph per selected holon, named by the holon, holding its direct content.
ex:City { ex:City ex:value "city" . }
ex:District { ex:District ex:value "district" . }
ex:Neighborhood { ex:Neighborhood ex:value "neighborhood" . }

In SPARQL-H, FROM HOLON ex:City SCOPE AGGREGATED FROM NAMED HOLONS queries this dataset; GRAPH ?h { ?s ex:value ?v } binds ?h to the holon each value came from.

Validation with SHACL

The vocabulary supplies five partial shapes. Full validation also follows the checklist below; basic RDF-H validity does not require composition support.

Validation and Reasoning Terms

Validation checks data against stated requirements. The Shapes Constraint Language (SHACL) expresses requirements as shapes. A shapes graph is an RDF graph containing those definitions. The effective shapes graph is the combined set of shapes used for one validation request.

Reasoning, or entailment, derives statements from other statements and rules. An entailment regime specifies which rules apply; an ontology supplies vocabulary definitions and reasoning rules. Simple entailment uses RDF's basic matching rules without additional RDFS or OWL rules. The Web Ontology Language (OWL) can supply such additional rules. Validation and reasoning are different operations.

A union combines graphs and keeps each distinct triple once. When combining independent sources, standardizing blank nodes apart means giving their blank nodes distinct internal identities to avoid accidental merging. A snapshot is a fixed version of the input data. Provenance records where data came from or how it was produced.

Independent shape imports

h:importsShapes identifies an IRI-named shapes graph supplied in the validation dataset. It identifies a graph, not a node shape. It MUST NOT be expanded through sh:node. A processor MUST NOT dereference the IRI to fetch the shapes graph from the Web unless the application has configured that behavior. For validation at H, the effective shapes graph is the RDF union of shapes graphs explicitly imported by H. Imports declared by ancestors are not inherited. Shape imports are non-transitive; a missing shapes graph is the missing-shapes-graph error.

Shape reuse within an imported graph uses standard SHACL references to individual shapes, such as sh:node or sh:and. There is no automatic nearest-ancestor fallback or ancestor-wide accumulation.

Content imports MUST NOT import shapes. Shape imports MUST NOT import content.

First form the union, preserving shared blank nodes within one shapes dataset and giving blank nodes from independently loaded sources distinct identities. The effective shapes graph MUST satisfy SHACL syntax rules before data validation. Conflicting definitions of the same shape IRI can make this union ill-formed; processors MUST report a shapes-definition failure (the ill-formed-shapes-graph error condition), not a data violation. Well-formed but unsatisfiable constraints produce ordinary SHACL violations. There is no override or replacement rule.

What a validation request declares and what its report identifies are stated in the validation checklist.

Required Checks

h:AssertedBaseTripleShape checks that every reifier-filed statement is also asserted. It uses SPARQL 1.2 triple-term patterns [[SPARQL12-QUERY]] and requires a processor supporting those patterns, or an equivalent component-extraction procedure. Dataset-profile membership satisfies this rule by construction.

h:CompositionHierarchyShape checks at most one immediate parent and rejects parent cycles. Apply it to the composition declarations graph only when using composition. Cycles in external domain relations are not RDF-H hierarchy violations.

h:ReifierMembershipShape checks nonempty reification and membership node kinds. h:ContentGraphMappingShape checks mapping cardinality and graph-name kinds. Full validity also requires the procedural checks below.

Portability Advice

h:HolonIntegrityShape warns when a reifier's containing holon carries no explicit registry declaration in the validated graph: h:Holon or legacy h:CompleteHolon typing, or an h:contentGraph mapping. This is advisory and does not invalidate a graph; the registry rule itself is checked procedurally against M. Under RDFS entailment the range of h:inHolon supplies h:Holon typing, so run the shape without entailment to surface omissions.

Application Completeness Claims

RDF-H does not establish that all relevant domain facts are known. The legacy h:CompleteHolon class is deprecated and remains a subclass of h:Holon for compatibility. Its presence registers a holon but MUST NOT, by itself, justify treating missing content as false or absent in the world.

Document the Contract

Applications may publish a separate, explicitly identified completeness contract using their own vocabulary: holon, subject scope, predicates or shapes, snapshot, provenance, and any filtering. A SHACL pass establishes only satisfaction of the specified constraints, not universal completeness. Such a claim is an application contract, not RDF-H core conformance. A filtered view does not establish completeness of hidden data.

Security and Privacy Considerations

Integrity of M. M decides what is a holon, where content lives, and how units are organized. Whoever can write M can redirect content, make a unit disappear from the registry, or add imports. In the dataset profile M defaults to the default graph, so a store whose default graph is writable by untrusted parties has an untrusted registry. Processors MUST obtain M from a source the application trusts, and publishers SHOULD keep M separate from content that untrusted parties may edit. Management statements that appear only in content never affect processing, which limits what a content writer can do, but it does not protect M itself.

No automatic dereferencing. Holon IRIs, graph names, import targets, and shapes-graph IRIs are identifiers. A processor MUST NOT fetch documents from these IRIs during resolution or validation unless the application has configured that behavior; doing so would let a data author cause network requests and inject remote shapes or content.

Exposure through G. Every filed statement is also asserted in G, and a statement filed in several holons is reachable through each of them and through any unselected graph. Hiding a holon does not hide its statements. Applications that filter by holon MUST apply the same policy to G and to every other scope that can reach the statement, and MUST disclose filtering in reports as the validation and query sections require.

Occurrence metadata. Reifiers carry sources, timestamps, and other occurrence metadata that is asserted and queryable even when the base statement is unremarkable. Publishers SHOULD review occurrence metadata before exchange and SHOULD NOT attach completeness claims to confidentially filtered data. Stable IRI reifiers make occurrences linkable across exchanges; applications that need that linkability SHOULD use IRI reifiers, and applications that do not want it SHOULD use blank-node reifiers.

Personal data. A holon identifier may also identify the described resource, including a person, and the parent hierarchy may reveal organizational membership. The registry, hierarchy, and occurrence metadata are personal data when they concern people and are subject to the same protection as the content.

Resource consumption. Aggregated and visible scopes union many graphs; a deep or wide hierarchy, a holon with many descendants, or many imports can make a request expensive, and a cyclic parent relation would not terminate without the acyclicity check. Engines handling untrusted data SHOULD bound hierarchy depth, scope size, and query cost. A processor MUST detect a parent cycle and report parent-cycle before returning any aggregated or visible scope graph, and MUST NOT rely on resource limits to terminate traversal of a cyclic relation.

Blank-node correlation. Scope graphs preserve the blank-node identities of the source dataset. Two statements that share a blank node remain correlated in every scope that contains both, even when the application intended the holons to be independent.

Internationalization Considerations

RDF-H introduces no new string-bearing constructs. Content statements, including language-tagged and RDF 1.2 directional literals, pass through filing, scope resolution, and conversion unchanged. Holon identifiers and graph names are IRIs and may contain non-ASCII characters as permitted by RDF. The vocabulary's labels and comments are English; translations may be added to the vocabulary document without changing term identity. Turtle-H and SPARQL-H keywords are ASCII and case rules are stated in those specifications.

This specification defines two classes of conformance: RDF-H Processor (a software component that consumes or produces RDF-H graphs) and RDF-H Graph (a holonic graph: a body of RDF data that uses the RDF-H vocabulary, together with the metadata context M that registers its holons; in the dataset profile M is normally part of the data). The criteria below summarize requirements stated normatively in the preceding sections. The processing algorithm is testable through its named error conditions; the requirement trace links each reviewed requirement to fixtures, and the implementation checks list the requirements that are verified by review instead.

Declare Capabilities Separately

A processor MUST declare its supported representation or representations. It MUST separately declare whether it supports composition, validation, conversion, Turtle-H, and SPARQL-H. Support for one capability does not imply another.

Representation Support

The dataset profile requires RDF datasets and named-graph extraction. The reifier profile requires RDF 1.2 triple terms and reifier membership. Triple-term validation needs an appropriate query engine or an equivalent component-extraction procedure. Implementations MAY support either profile or both; Turtle-H support is independent.

Core Requirements

A conforming RDF-H graph or dataset, judged together with its M, MUST be valid RDF for its declared representation, satisfy the content mapping rules, and satisfy the additive invariant: each filed statement is also asserted.

A conforming processor MUST support its declared representation's extraction rules and report invalid mappings. A converter MUST preserve M (adding only reported derived mappings), holon identity, and direct content, and declare its content- or assertion-preservation level. A reasoning or validation service MUST declare its scope and regime as specified in the relevant sections.

Basic conformance does not require a parent, a root, domain parthood, descendant aggregation, or Turtle-H support.

Registry-aware conformance uses the processing context and registry. Membership extraction alone does not claim registry-aware processing.

Optional Composition Requirements

A processor claiming composition MUST enforce direct-parent cardinality and acyclicity, resolve visible scope using descendants and direct imports, and resolve only explicit shape imports. Multiple roots are permitted. Resolution errors MUST be reported.

Implementation Checks

The executable fixtures cover visible scope, explicit shape imports, dataset separation, parent cardinality, and hierarchy cycles. The RDF-H test manifest tests the optional conversion and validation capabilities through the same adapter protocol: content preservation in both directions, the non-promotion of content into M, derived blank-node mappings, assertion preservation, per-holon shape selection without inheritance, scope-dependent validation outcomes, and both shape error conditions.

Every error condition of the processing algorithm has at least one test, and the SPARQL-H suite resolves scopes over sources in both profiles. Requirements not exercised by the current offline adapters are assessed by documentation and review: how M is obtained and trusted, the prohibition on dereferencing identifiers, the disclosure of authorization filtering, and the declaration of supported capabilities. Instrumented integration tests can monitor network requests, exercise denied-access and filtered-view responses, and inspect capability declarations; M trust policy still requires deployment review.

Conversion and Extraction

A converter changes data from one RDF-H representation to another. A round trip converts to another representation and back. A preservation level states what information must survive conversion. Unfiled statements are asserted statements that are not assigned to any holon. Occurrence metadata is information attached to a particular reifier, such as its source.

A converter MUST declare one of two preservation levels:

Conversion preservation levels
LevelRequired preservation
Content-preserving (minimum)M, registered holon identities, each CG(H), base assertions of filed statements, and empty registrations.
Assertion-preservingEverything above and every asserted source statement, including unfiled provenance and occurrence metadata, up to a consistent blank-node renaming.

A content-preserving converter MAY discard unfiled assertions or occurrence metadata only when it explicitly reports every loss or a documented, complete loss category. An assertion-preserving converter MUST NOT discard those statements; it MUST fail if its target representation cannot preserve them. Neither level permits discarding a statement explicitly filed in a holon.

Before reporting success, a converter MUST verify that the target is valid for its declared representation, retains the registry and M (apart from reported derived mappings), preserves every CG(H), and meets the declared assertion-preservation level. If no target can meet these requirements, it MUST fail with unrepresentable-conversion, a conversion error distinct from the scope-resolution errors. In particular, holons that select the same target graph must have identical direct contents; their contents must not be silently merged. Retaining a dataset-profile assertion using h:inHolon can activate it in a reifier target: if that makes the target invalid or changes any CG(H), conversion must fail, even at the content-preserving level when that assertion is filed. New graph names and occurrence reifiers must be fresh with respect to retained identifiers. An existing blank-node holon mapping must be retained.

  • Reifiers to named graphs: place each reified content member in the graph selected by H's mapping in M; retain M as the metadata context. A blank-node holon without an existing mapping has no default graph name, so the converter MUST add an explicit h:contentGraph mapping for it to the output M, naming a fresh graph. Adding such a derived mapping is the only change to M a converter may make, and it MUST be reported.
  • Named graphs to reifiers: emit each content member as a base statement and a fresh occurrence reifier linked to H. Retain M separately.
# Input, reifier profile. M (supplied as a view of the same graph): _:h a h:Holon .
ex:a ex:value "a" .
_:r1 rdf:reifies <<( ex:a ex:value "a" )>> ; h:inHolon _:h .

# Output, dataset profile. The default graph is the output M.
_:h a h:Holon ; h:contentGraph <urn:example:derived-1> .   # derived mapping, reported
<urn:example:derived-1> { ex:a ex:value "a" . }

# Reported: derived h:contentGraph mapping for _:h; loss category: the membership record _:r1.

Retained unfiled assertions, including source membership records (rdf:reifies and h:inHolon) and occurrence metadata, MUST NOT be placed in the graph that serves as M for the output. A converter targeting the dataset profile MUST either supply the output M as a separately identified graph or place unfiled assertions in a named graph that is not M and not a content graph. Retained source membership records remain ordinary assertions in the output; they do not make the output mixed-representation data unless the converter declares it so.

Graph placement, reifier identity, and occurrence multiplicity are preserved only when the converter explicitly claims and implements those additional guarantees. Content-preserving round trips guarantee registry, M, and content equality, not full source-dataset equality; M equality is up to the derived blank-node mappings that a dataset-profile conversion reports. Compare M and content jointly with one consistent blank-node renaming.

Extraction precedes entailment and uses set semantics. Preserve shared blank nodes across a source dataset; standardize independently loaded inputs apart before merging. A holon SHOULD use one representation. For declared mixed data, CG(H) is the union of the triples filed by explicit reifier memberships, read from every graph of S, and the selected named graph, as step 4 states; reifier-filed members MUST still have base assertions, which may be in any graph of S or in M. Mixing representations MUST NOT change M.

@prefix h: <https://w3id.org/rdf-h#> .
@prefix ex: <https://example.org/> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .

ex:City a h:Holon .                               # M is the default graph
ex:Extra ex:value "extra" .                       # base assertion in the default graph
_:r1 rdf:reifies <<( ex:Extra ex:value "extra" )>> ; h:inHolon ex:City .
_:r2 rdf:reifies <<( ex:Elsewhere ex:value "elsewhere" )>> ; h:inHolon ex:City .

ex:City { ex:City ex:value "city" . }             # named-graph content of ex:City
ex:Other { ex:Elsewhere ex:value "elsewhere" . }  # base assertion of the second membership

With mixed data declared, CG(ex:City) holds the city, extra, and elsewhere statements: the named graph plus both reifier-filed triples, whose base assertions sit in two different graphs. Without the declaration, the dataset profile applies and only the city statement is content.

Design Rationale

The word holon comes from Koestler [[KOESTLER-1967]]: something that is a whole in its own right and at the same time a part of a larger whole. RDF-H keeps exactly that double nature and nothing more. A holon is a whole because it has its own explicitly filed content, which can be read, validated, and exchanged on its own. It is a part because a parent link can place it under another holon, whose aggregated scope then includes it. Imports add the lateral dependencies that a strict hierarchy cannot express. The three scopes are the three ways of reading a holon: alone, with everything organized under it, or with what it explicitly draws in. What RDF-H does not model is equally deliberate: domain parthood (a floor is physically part of a building) is a claim about the world and belongs in content, under a domain vocabulary; behaviour, autonomy, and change over time are outside an organization of statements.

One parent. A holon has at most one administrative parent, so the hierarchy is a forest. This gives each holon one administrative path upward and simplifies ownership and updates. A DAG could also have unambiguous set-union aggregation; it would require policies for multiple administrative parents. Imports provide lateral reuse of direct content, but do not reproduce a second parent's recursive descendant aggregation. Applications needing that behavior must enumerate the required imports or use distinct holons related through an application vocabulary.

No ancestor scope. A part does not silently see its context. Aggregated scope reads downward only, so a holon's content means the same wherever the holon is placed, which is what makes a holon reusable. When a part does need its context, the author says so with an import of the parent.

Single-hop imports. An import adds one holon's direct content and nothing it imports or contains in turn. Transitive imports would make a scope depend on declarations in additional holons and require an explicit closure policy, including cycle handling. Chains are written explicitly, import by import.

The additive invariant. Filing never changes whether a statement is asserted, so the data uses ordinary RDF terms and assertions. RDF-H interprets the union of source graphs and M as G; ordinary SPARQL default-graph queries do not automatically read that union. Holon-unaware consumers retain their usual dataset-selection behavior. The price is that RDF-H cannot hold hypothetical or contextual statements that are filed but not asserted; those need a separate mechanism, listed under future work.

An explicit registry. Which holons exist and how they are organized is stated in M, never inferred from content or entailment. A dataset cannot reorganize itself through a statement that happens to use a management predicate, and a reasoner cannot create or dissolve holons.

Two profiles. Named graphs are the natural storage when each holon's content is edited and queried as a unit; reifiers are needed when the same statement is filed in several holons with different occurrence metadata, or when content must travel in a single graph. Both describe the same abstract content, which is why conversion between them is specified.

Attribution. A scope graph is a union, so it does not say which holon each statement came from. When that matters, the attributed scope dataset keeps each selected holon's content as a named graph beside the union; SPARQL-H exposes it with FROM NAMED HOLONS.

Relationship to Other Specifications

RDF-H combines several existing mechanisms rather than replacing them.

  • RDF 1.1 datasets and TriG [[RDF11-DATASETS]] [[TRIG]]. RDF 1.1 deliberately assigns no formal semantics to named graphs. The dataset profile supplies one application-level reading: a named graph selected by M is the direct content of a holon, and every graph's statements are asserted. Datasets that do not use the RDF-H vocabulary are unaffected.
  • RDF 1.2 reifiers [[RDF12-CONCEPTS]]. The reifier profile uses rdf:reifies exactly as RDF 1.2 defines it and adds one property, h:inHolon. RDF-H does not change the meaning of triple terms, which remain unasserted; the additive invariant requires the base assertion separately.
  • SHACL [[SHACL]]. SHACL lets a data graph name its shapes graphs with sh:shapesGraph and lets shapes graphs include others with owl:imports. h:importsShapes differs in granularity: it selects shapes per holon, in M, without transitive inclusion, so that one dataset can hold holons validated under different shapes.
  • OWL imports [[OWL2-SYNTAX]]. owl:imports merges ontologies transitively for reasoning. h:imports selects content for one holon's visible scope, is not transitive, and has no entailment consequences.
  • SPARQL Service Description and VoID [[SPARQL11-SERVICE-DESCRIPTION]] [[VOID]]. Both describe which graphs or datasets an endpoint offers. They can describe a store that holds RDF-H data, but they do not define content units, hierarchy, or scope resolution. A service description could list the scope graph exposed by a scoped endpoint.
  • PROV bundles [[PROV-O]]. A prov:Bundle is a named set of provenance descriptions. A holon's content is not provenance about its statements; occurrence metadata on reifiers may itself be described with PROV.
  • Nanopublications [[NANOPUB]]. A nanopublication fixes a structure of assertion, provenance, and publication-information graphs linked from a head graph. A nanopublication's assertion graph can be the content graph of a holon, with M playing the role of the head graph for many publications; RDF-H does not prescribe the provenance and publication-information parts.
  • Linked Data Platform [[LDP]]. LDP containers organize resources through HTTP interactions and membership triples about resources. RDF-H memberships are about statements, and RDF-H defines no protocol.

Change Log

0.8 (2026-10-21)

Separated Turtle-H, clarified content and assertion semantics, and introduced optional administrative composition. This draft also consolidates repeated explanations and keeps conversion details in an appendix; vocabulary and semantics are unchanged by that editorial cleanup.

Migration from 0.7: RDF-H no longer defines its specialized part-whole vocabulary, parthood cycle checks, or mereological coherence shapes. Use an external domain vocabulary for domain parthood. Use h:parentHolon only for administrative organization; it is not a semantic replacement for domain parthood.

Changes in this release, in order of introduction:

  • Hierarchy aggregation includes the selected holon and its descendants; ancestors are excluded unless explicitly imported. Direct named-graph queries remain direct. Imports contribute only their target's direct content; descendant aggregation inherits neither imports nor shapes.
  • Shapes: the assertion shape is unchanged; h:HolonIntegrityShape warns on any missing registry declaration rather than only missing h:Holon typing; h:AcyclicPartShape is replaced by h:CompositionHierarchyShape, which checks h:parentHolon cardinality and acyclicity.
  • Several holons may select the same content graph; graph names are not reserved per holon.
  • Conversion: where converters place unfiled assertions, and derived blank-node mappings as the only permitted change to M.
  • Registry and mapping validity is checked over all of M for every request.
  • Global scope is defined for validation and reasoning; RDF-H Graph conformance is judged together with M; the blank-node scope rule for a separately supplied M.
  • A processing algorithm with named error conditions and a profile-selection rule, including declared mixed data. The algorithm is the single normative statement of holon resolution; the processing-context, hierarchy, and scope sections explain it and link to the governing steps.
  • Security and privacy considerations replace the authorization note; internationalization and related-work sections are added.
  • The Turtle-H suite is executed by an implementation for the first time: the RDF4J-based rdf4j-rio-turtleh parser passes its parsing and expansion cases.
  • The SPARQL-H suite gains reifier-profile tests, so both profiles are executed.
  • An RDF-H test manifest covers the optional conversion and validation capabilities.
  • The attributed scope dataset keeps each selected holon's content as a named graph beside the scope union; SPARQL-H exposes it with FROM NAMED HOLONS. Mixed data is specified fully and tested. A design rationale explains the single parent, the absence of an ancestor scope, single-hop imports, the additive invariant, and the explicit registry.
  • Self-review: the conversion error joins the error table; mixed data no longer rejects an unmapped blank-node holon; global reasoning requests need no holon; a reifier-profile request over a dataset designates its graph; an undefined scope name is an unsupported-capability error.
  • Editorial: the processing algorithm, security, and internationalization are top-level sections; validation material is consolidated; the design rationale and related work are appendices; examples are numbered and tables captioned.
  • Every error condition of the processing algorithm gains a test, shown in the error table; the Turtle-H and SPARQL-H suites gain tests for previously untested rules, and each specification lists the requirements verified by review rather than by tests.
  • The Turtle-H suite gains serialization tests for the serializer conformance class; rdf4j-rio-turtleh passes them.

This revision separates authoritative M from content in both representations, defines the registry and mode-specific errors, adds two conversion preservation levels, deprecates unsupported completeness semantics, and distinguishes shapes-definition failures from data violations.

Draft Status and Future Work

Vocabulary publication
The vocabulary redirect and stable publication artifacts remain to be completed. The namespace document is https://w3id.org/rdf-h#; each release has a version IRI of the form https://w3id.org/rdf-h/0.8, which the redirect is to serve. Release 0.7 used the fragment form https://w3id.org/rdf-h#0.7, which is kept as its prior-version IRI.
Turtle-H base-language coverage
The Turtle-H suite tests the @holon extension, not inherited Turtle 1.2 syntax. Running the W3C Turtle 1.2 test suite through Turtle-H parsers would show that blocks leave the base language intact.
Contextual assertions
Local theories and hypothetical statements require separate future work; they are outside the additive core.
Independent implementations
Reference adapters execute the SPARQL-H suite over both profiles and declared mixed data (84 of 84) and the RDF-H conversion and validation suite (14 of 14), and the RDF4J-based rdf4j-rio-turtleh parser executes the Turtle-H suite (81 of 81, including serialization and an unrepresentable-context rejection), both with EARL reports. Both come from the editors' organization, so neither is independent evidence. Advancement beyond a community draft needs at least two independent implementations of each feature with EARL reports.
Dependency maturity
The evolving RDF/SPARQL dependencies are pinned to RDF 1.2 Concepts (Candidate Recommendation Snapshot, 7 April 2026), RDF 1.2 Semantics (Candidate Recommendation Draft, 24 September 2026), Turtle 1.2 (Working Draft, 7 October 2026), and SPARQL 1.2 Query (Working Draft, 11 October 2026). The reifier profile, asserted-base-triple shape, and companions depend on these evolving documents. Their maturity must be reassessed before RDF-H stabilizes.
Namespace under W3C
If adopted by a W3C group, the namespace would move from https://w3id.org/rdf-h# to a W3C-managed IRI; the w3id namespace would then redirect.
Media type
Turtle-H proposes text/turtle-h in its registration template; IANA registration follows stabilization.
Qualified completeness
Application contracts can qualify completeness; a shared machine-readable claim vocabulary needs further design.
