A holon is an identifiable unit of RDF content. SPARQL-H adds FROM HOLON to SPARQL to query the statements assigned to a holon. The query can also select related content through parent links and explicit imports, as defined below.

This document is the frozen snapshot of SPARQL-H 0.1.0, released with RDF-H 0.8 on 2026-10-21 (repository tag sparql-h-v0.1.0). The editor's draft may be newer.

This is experimental community draft 0.1.0 by Geoknoesis LLC, targeting RDF-H 0.8. It is not a W3C specification and is not accepted by ordinary SPARQL parsers. RDF-H does not require this extension; standard SPARQL recipes remain available.

Feedback and source are in the repository. The document and examples use the Apache 2.0 license.

Terms Used in This Specification

This specification assumes basic SPARQL knowledge. An RDF graph is a set of subject, predicate, and object triples. A dataset contains a default graph and zero or more named graphs. Ordinary query patterns read the default graph; GRAPH patterns select named graphs.

A holon's direct content, written CG(H), is the set of triples explicitly assigned (or filed) in holon H. A parent link, written h:parentHolon, organizes a child under an immediate parent. Following these links upward reaches ancestors; following them downward reaches descendants. An import, written h:imports, explicitly selects another holon's direct content.

A scope selects content for a query. DIRECT selects only H's direct content. AGGREGATED, written AG(H), adds all descendants' direct content. VISIBLE, written VG(H), also adds the direct content of holons imported by H. These names describe data selection, not access permissions or SPARQL functions such as COUNT.

The source is the RDF-H data supplied by the calling application. Its metadata context M is the graph of declarations that control registration, graph mappings, parent links, and imports. Its registry K(M) is the set of holons explicitly registered by those declarations. A graph mapping selects the named graph containing a holon's direct content. RDF-H defines the exact registration and mapping rules.

Scope resolution reads these declarations and combines the selected content into a scope graph. Combining graphs uses a set union: each distinct triple appears once. The query dataset is the dataset supplied to the SPARQL engine after this step; it differs from the source dataset.

An IRI is an identifier such as https://example.org/City. RDF-H's dataset profile (also called the dataset representation) stores holon content in named graphs. Its reifier profile uses RDF resources called reifiers linked to triple terms, which represent triples without asserting them. A blank node identifies a resource without an IRI; its identity must remain consistent when selected graphs are combined.

An entailment regime specifies the reasoning rules used during evaluation. Simple entailment uses basic RDF matching without additional RDF Schema or OWL rules. An ontology supplies vocabulary definitions and reasoning rules. A service profile is an optional set of additional requirements for an endpoint that accepts queries over a network. A snapshot is a fixed version of the source data.

One Clause Selects the Scope

PREFIX ex: <https://example.org/>
SELECT ?subject ?value
FROM HOLON ex:City SCOPE AGGREGATED
WHERE { ?subject ex:value ?value }
ORDER BY ?value

The processor combines the city's content and its descendants' content into one default graph, then evaluates the remaining query with a standard SPARQL engine. The source dataset is supplied by the application or endpoint.

Holon clauses and the default graph they select
ClauseDefault graph
FROM HOLON ex:CityDirect city content; DIRECT is the default.
FROM HOLON ex:City SCOPE DIRECTDirect city content.
FROM HOLON ex:City SCOPE AGGREGATEDCity content and all administrative descendants' direct content.
FROM HOLON ex:City SCOPE VISIBLEAggregated city content plus the direct content of holons explicitly imported by the city.
FROM HOLON ex:City SCOPE AGGREGATED FROM NAMED HOLONSAs for AGGREGATED, and each selected holon's direct content is also a named graph, named by the holon's IRI, so GRAPH ?h tells which holon a statement came from.

The three scope names select data. They do not change SPARQL aggregate functions such as COUNT.

Scope and Dependencies

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here. Examples and sections marked informative are explanatory; other sections define requirements. RDF-H defines holon identity, direct content extraction, graph mappings, hierarchy, and imports [[RDF-H]]. This specification only adds query syntax and its evaluation contract.

Version 0.1.0 supports outermost SELECT, ASK, and explicit-template CONSTRUCT queries over SPARQL 1.1-compatible content graphs [[SPARQL11-QUERY]]. The grammar positions it uses are unchanged in SPARQL 1.2 [[SPARQL12-QUERY]], and a processor built on a SPARQL 1.2 engine applies the same rules; evaluating reifier-profile content that contains triple terms requires SPARQL 1.2. It defines no updates, new result format, media type, or HTTP protocol parameter. DESCRIBE, template-less CONSTRUCT shorthand, multiple holon clauses, and holon clauses inside subqueries are outside this version and MUST be rejected in SPARQL-H input.

A processor MUST declare support for the RDF-H dataset representation, reifier representation, or both. A reifier processor needs RDF 1.2-capable content extraction; this draft does not add triple-term syntax to SPARQL 1.1. It MUST reject extracted content it cannot faithfully evaluate, rather than drop unsupported terms. Turtle-H support is independent.

Syntax

Use one holon clause where the outer query's ordinary dataset clauses would occur: after the SELECT clause, after the CONSTRUCT template, or after ASK. The query body and solution modifiers follow unchanged.

The rules below use EBNF (Extended Backus–Naur Form). ::= defines a rule, | separates alternatives, and ? makes the preceding group optional. Prologue contains BASE and PREFIX declarations; ConstructTemplate describes output triples; WhereClause contains query patterns; SolutionModifier covers grouping, ordering, and limits; and ValuesClause supplies trailing VALUES bindings, if present. Other rule names retain their SPARQL 1.1 definitions.

QueryUnitH        ::= Prologue (SelectQueryH | ConstructQueryH | AskQueryH) ValuesClause
SelectQueryH      ::= SelectClause HolonDatasetClause WhereClause SolutionModifier
ConstructQueryH   ::= 'CONSTRUCT' ConstructTemplate HolonDatasetClause WhereClause SolutionModifier
AskQueryH         ::= 'ASK' HolonDatasetClause WhereClause SolutionModifier
HolonDatasetClause ::= 'FROM' 'HOLON' iri ('SCOPE' ScopeMode)? NamedHolonsClause?
ScopeMode         ::= 'DIRECT' | 'AGGREGATED' | 'VISIBLE'
NamedHolonsClause ::= 'FROM' 'NAMED' 'HOLONS'

Unchanged productions, whitespace, comments, IRI escaping, BASE and PREFIX resolution follow the SPARQL 1.1 grammar. ValuesClause includes its ordinary empty alternative. Keywords are case-insensitive, with standard token boundaries. The new keywords apply only in the positions defined here; matching words inside comments, strings, or IRIs are not clauses.

A keyword token ends at whitespace, a comment, or a character that cannot continue a name; a following : continues a prefixed name instead. The characters HOLON: (in any case) therefore begin the SPARQL prefixed name HOLON:…, never the HOLON keyword, so FROM HOLON:City is an ordinary FROM clause and the query contains no holon clause. A processor MUST NOT read it as FROM HOLON :City. A prefixed holon name MUST be separated from HOLON by whitespace or a comment; an IRI reference such as HOLON<https://example.org/City> needs no separator, as in SPARQL.

  • The holon is a constant IRI, written as an IRI reference or prefixed name. Variables, literals, and blank-node labels are not allowed.
  • Omitting SCOPE means DIRECT. Unknown scope names are errors; processors MUST NOT substitute another scope.
  • Exactly one outermost holon clause is required. Ordinary FROM and FROM NAMED clauses MUST NOT be combined with it. FROM NAMED HOLONS is the only named-graph selector; it takes no IRI and follows the scope, when one is given.
  • Ordinary SPARQL subqueries are allowed and inherit the selected query dataset; they MUST NOT contain a holon clause.

A service MAY also accept ordinary SPARQL without a holon clause. Such input is ordinary SPARQL, not an implicit SPARQL-H query; the service MUST preserve its normal dataset semantics and MUST be able to report that the input was not treated as SPARQL-H. A conformance adapter answers a SPARQL-H syntax request for such input with a syntax rejection, not with acceptance.

Evaluation

Resolve the Source

The query request MUST identify a source data graph or dataset and the representation used. Resolve BASE and PREFIX declarations before looking up the holon. Resolving a holon IRI MUST NOT automatically fetch a document from that IRI on the Web.

The selected holon MUST be known under the declared RDF-H representation; an unknown holon is a resolution error. A known empty holon is valid and produces an empty direct graph. Apply RDF-H content-graph mappings and import-resolution errors. A missing named graph for a known holon means empty content, not an unknown holon.

Evaluation is defined over one fixed set of inputs: the source data and M. Implementations MUST produce results equivalent to that context; transaction mechanisms, revision identifiers, and caching are service concerns discussed in the service profile.

The query request supplies the RDF-H processing context, including M. For dataset input, M defaults to the source default graph. Reifier input must explicitly supply M; it is never inferred from arbitrary asserted content. Known holons are exactly K(M). Apply the checks of the RDF-H processing algorithm for the requested scope: DIRECT ignores hierarchy/import errors; AGGREGATED and VISIBLE validate the complete parent relation in M; VISIBLE resolves only the selected root's direct imports. Inferred typing never registers a missing endpoint.

Build the Scope Graph

Use the RDF-H scope definitions. For selected holon H:

DIRECT     -> CG(H)
AGGREGATED -> AG(H) = union of CG(H) and every descendant's direct content
VISIBLE    -> VG(H) = AG(H) union direct content of targets imported by H

Descendants follow h:parentHolon+ toward H. Ancestors are excluded unless explicitly imported. Imports are single-hop: imports on ancestors or descendants are not inherited, and an imported target's descendants and imports are not expanded. Shape imports do not affect query content.

The scope graph MUST be a set union before query evaluation. A repeated triple appears once in that graph; normal SPARQL solution multiplicity still applies. Preserve shared blank-node identity across the original source dataset. Statements that record reifier memberships and other metadata enter the scope graph only if explicitly filed as content.

DIRECT requires only content extraction. AGGREGATED and VISIBLE require RDF-H composition support. A processor lacking that capability MUST report an unsupported-capability error, not fall back to DIRECT. Validate mappings and apply the mode-specific hierarchy and import checks before resolving the selected scope.

Only declarations in M participate. A management-predicate statement filed only as content does not affect resolution.

Evaluate Ordinary SPARQL

  1. Build a query dataset whose default graph is the scope graph. Without FROM NAMED HOLONS its named-graph set is empty; with it, the named graphs are those of the RDF-H attributed scope dataset: one per selected holon, named by the holon identifier (an IRI or a blank node, including blank-node descendants or import targets) and holding that holon's direct content.
  2. Remove the parsed holon clause from the query syntax tree, preserving all other query elements.
  3. Evaluate the resulting standard SPARQL query against that query dataset under the declared entailment regime.

Joins and property paths can cross statements originating in different selected holons because they are evaluated over the union graph. ORDER BY, grouping, LIMIT, OFFSET, and trailing VALUES keep their ordinary semantics.

Explicit GRAPH patterns keep their normal named-graph meaning. Without FROM NAMED HOLONS the query dataset has no named graphs, so those patterns contribute no matches; they MUST NOT be reinterpreted as a scope request. With it, GRAPH ?h binds ?h to each selected holon whose direct content matches, so a statement filed in several selected holons matches once per holon, while the default graph remains the deduplicated union. That does not imply every surrounding query is empty: OPTIONAL, UNION, and NOT EXISTS retain their normal semantics.

A processor MAY compute the scope graph as a view or evaluate it without storing a separate copy, provided the results are equivalent. It MUST NOT merely wrap a multi-pattern query in GRAPH ?g, which would constrain the patterns to one source graph and can miss cross-holon joins. Scope graphs are read-only views; executing the query MUST NOT modify holon content or memberships.

Reasoning Rules

When the caller supplies no entailment regime, the processor MUST use simple entailment. Explicit ontology inputs and supported regimes form part of the evaluation context. Extract asserted content and resolve the scope before applying query-time entailment. Inferences MUST NOT implicitly change hierarchy, import selection, or source memberships. A request names an entailment regime by IRI, as in [[SPARQL11-ENTAILMENT]]; simple entailment is http://www.w3.org/ns/entailment/Simple. A requested regime the processor does not support is an unsupported-capability error.

Processors MUST distinguish failure from a valid empty result. Error encodings and transport status codes are implementation-defined in this version; implementations MUST document them. Where a processor reports an error category, it SHOULD use the identifiers syntax, dataset-conflict, resolution, unsupported-capability, and execution; the conformance suite uses them to compare expected errors across implementations and additionally requires the exact RDF-H condition for fixtures that name one. A processor that reports finer detail SHOULD name the RDF-H error condition, such as parent-cycle, alongside the category.

Optional Service Profile

Core conformance covers syntax, scope resolution, query-dataset construction, and evaluation errors. An implementation claiming the optional service profile MUST also satisfy this section. This profile does not define a new network message format.

This draft defines no transport. A front end may receive source context through application configuration, a dedicated endpoint, or a documented API. A regular SPARQL endpoint cannot be assumed to parse FROM HOLON.

A SPARQL-H front end MUST reject standard protocol default-graph-uri or named-graph-uri dataset selectors combined with a holon clause. The source context is supplied separately; those selectors would otherwise conflict with the resolved query dataset. Ordinary SPARQL requests remain subject to the standard protocol's dataset precedence rules [[SPARQL11-PROTOCOL]].

Before reporting results, a processor MUST identify the source dataset or snapshot, resolved holon IRI, effective scope, source representation, entailment regime, and any filtering. Metadata may be returned alongside results; standard SPARQL result documents and variable bindings MUST NOT be changed to inject this information.

Scope selection grants no authorization. The service MUST either fail when selected data is not accessible, or explicitly report that the result uses a filtered view. It MUST NOT represent a filtered view as the full RDF-H scope. Scope and resolution errors occur before query evaluation and cannot be suppressed by a query's SERVICE SILENT.

Standard SERVICE patterns retain their remote-query meaning and are subject to host service policy. Local scope is not a remote-data or network-access boundary. A service rejecting federation MUST report that policy error; it MUST NOT silently reinterpret SERVICE as a local graph operation.

A service-profile processor MUST report the effective entailment regime and ontology inputs, a consistent source snapshot or equivalent revision context, and its service-profile claim. Core adapters may expose the same details without changing result bindings.

This produces four value statements.

A conforming SPARQL-H processor MUST parse the grammar and restrictions, preserve IRI resolution, implement DIRECT and its declared representation support, and support the three query forms defined here. It MUST implement AGGREGATED and VISIBLE when claiming composition support, or report the defined capability error.

A core processor MUST preserve the input context, shared blank-node identity, the query dataset as defined (default-only unless FROM NAMED HOLONS is given, which it MUST support), and specified error behavior. It MUST document supported representations, composition, and regimes. Services MAY additionally claim the optional service profile, including its metadata, transport-conflict, authorization/filtering, and federation requirements.

The RDF test manifest uses W3C manifest infrastructure with project-specific SPARQL-H test classes. See the suite guide for implementation adapters, result comparison, and EARL reporting. Manifest integrity and expected-result smoke checks do not establish parser conformance; a small reference adapter for both RDF-H profiles is supplied, with limits documented in the suite guide.

The reference adapter parses source using the grammar plus RDFLib base-language productions, and resolves scopes with a separate executable context model. It does not consume expected lowerings or results. It is a test implementation, not a production service or proof of independent multi-implementation interoperability.

The suite exercises the core requirements that a request and its result can show: syntax and its restrictions, both RDF-H profiles, every scope, the default-only query dataset, cross-holon joins, entailment defaults, and each error category. It does not exercise the optional service profile, for which this version defines no standard transport; the duties to declare capabilities and document error encodings; the prohibition on fetching holon IRIs; or read-only evaluation. Implementations show these by documentation and review. A documented service adapter can make transport conflicts, federation policy, filtering disclosures, network access, and read-only behavior testable; the lack of a standard transport does not make those duties inherently untestable.

Security and Privacy Considerations

The RDF-H security and privacy considerations apply to the source data, M, and scope resolution. SPARQL-H adds the usual SPARQL concerns: query cost, which aggregated and visible scopes can multiply; SERVICE patterns, which reach remote endpoints regardless of the local scope; and result metadata, which may reveal the registry and hierarchy to a querier who cannot otherwise read M; FROM NAMED HOLONS likewise exposes the identifiers of every selected holon as graph names. A service that filters by authorization reports the filtering as the service profile requires and never presents a filtered view as the full scope.

Implementation Guidance

A small front end can parse the extra dataset clause, resolve content with RDF-H's existing standard SPARQL scope recipes, and hand the lowered query and scope graph to an existing engine. This is a query-and-context translation, not a universally self-contained SPARQL string rewrite.

Extend a parser or use a token-aware grammar. A regular-expression replacement can corrupt literals, comments, IRIs, or nested queries. Preserve source positions for diagnostics. Cache scope graphs only with a source revision, holon, scope, authorization context, and regime sufficient to prevent stale or cross-user reuse.

Materialization is adequate for a prototype; virtual unions and indexed descendant traversal can avoid large copies. Keep the same result semantics, especially cross-holon joins and duplicate elimination before aggregates.

Draft Status

0.1.0 introduces one holon clause, three scope modes, default-only query datasets with an optional FROM NAMED HOLONS attribution selector, and read-only SELECT, ASK, and explicit-template CONSTRUCT. An experimental reference adapter for both RDF-H profiles parses source queries; no standard endpoint or full RDF 1.2 query support is claimed.

Future work: independent implementation interoperability, transport negotiation, test coverage for SPARQL 1.2 query features such as triple-term patterns, and DESCRIBE. Any extension must preserve the distinction between direct content and explicit scope resolution.
