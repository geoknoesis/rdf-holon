Turtle-H adds an @holon block to Turtle 1.2. A block assigns its statements to a holon, an identifiable unit of RDF content. A parser expands the block into RDF 1.2 statements that record both the claims and their holon membership.

This unofficial community draft is produced by Geoknoesis LLC. It is not a W3C specification. This working revision defines the syntax, staged expansion, and metadata output for RDF-H 0.8.

Relationship to RDF-H

This specification targets RDF-H 0.8. RDF-H defines holon identity, content, assertion semantics, and serialization profiles; this document defines authoring syntax.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in BCP 14 [[RFC2119]] [[RFC8174]] when, and only when, they appear in all capitals, as shown here. The prefix h: denotes https://w3id.org/rdf-h# and rdf: denotes http://www.w3.org/1999/02/22-rdf-syntax-ns#.

Terms and Parser Outputs

An RDF triple is a subject, predicate, and object statement. An asserted triple is included as a claim in the data. A graph is a set of triples; duplicates count once. To file a triple means to assign it to a holon's content.

An IRI is an identifier such as https://example.org/City. A blank node identifies a resource without an IRI. A triple term, written <<( :s :p :o )>>, represents a triple without asserting it [[RDF12-CONCEPTS]]. A reifier is an IRI or blank node linked to that term by rdf:reifies. The property h:inHolon assigns the reified statement to a holon. This is RDF-H's reifier representation. An occurrence is one separately identified record of a statement.

Expansion (also called desugaring) replaces block shorthand with explicit RDF statements. The parser returns two graphs: G, the asserted data, and M, the metadata context. M contains declarations that register holons, select storage graphs, organize parent links, and specify imports. Content statements do not control these operations unless they are also explicitly included in M.

A parent link organizes one holon under another using h:parentHolon. It does not assert physical parthood. An import uses h:imports to select another holon's direct content for a visible-scope query. A holon's direct content, written CG(H) for holon H, is the set of triples filed in it. A visible-scope query combines that content, the content of holons below it in the parent hierarchy, and the direct content of holons it imports.

A dataset contains a default graph and zero or more named graphs. RDF-H's dataset profile stores holon content in those named graphs. TriG is a syntax for writing RDF datasets; Turtle-H blocks instead use the reifier representation.

The grammar uses EBNF (Extended Backus–Naur Form): | means an alternative and * means zero or more repetitions. Turtle abbreviations, including prefixed names such as ex:City, follow Turtle 1.2.

Writing Holon Blocks

Turtle-H adds @holon blocks to Turtle 1.2. A parser returns asserted RDF data G and an explicit metadata context M for RDF-H processing.

The @holon Directive

Assign statements to a holon using the @holon directive, followed by the holon's identifier (IRI or blank node) and a block of Turtle statements enclosed in curly braces: 

@holon <holon-iri> {
    # Turtle statements that are constituents of this holon
}

Why a directive (not a bare IRI { ... } block)? The bare-brace form denotes a named graph in TriG [[TRIG]]; reusing it would clash with that vocabulary. The @holon keyword makes Turtle-H grammatically distinct from TriG and unambiguous to a single parser pass. Turtle-H is not part of Turtle 1.2 [[RDF12-TURTLE]] — it is a proposed sugar that lets developers write a statement once and have a Turtle-H-aware parser generate both the asserted triple and the h:inHolon annotation.

Content does not create hierarchy. An @holon block files statements in a holon. Writing one block inside another creates neither an administrative parent nor domain parthood. Declare h:parentHolon explicitly to organize holons. Domain relations can use an external vocabulary.

@prefix ex: <https://example.org/> .
@prefix h: <https://w3id.org/rdf-h#> .

ex:Car_123 a h:Holon .
ex:Engine_456 a h:Holon .

@holon ex:Car_123 {
    ex:Engine_456 ex:componentOf ex:Car_123 .

    @holon ex:Engine_456 {
        ex:Piston_789 ex:componentOf ex:Engine_456 .
    }
}

This concise syntax is syntactic sugar for the standard RDF 1.2 representation. A Turtle-H parser expands it into standard triples as the expansion algorithm specifies.

The block @holon :H { :s :p :o . } desugars per Turtle-H into:

  1. The Base Fact: The relationship itself is asserted.
    :s :p :o .
  2. The Membership Record: The relationship's reifier is linked to its containing holon.
    << :s :p :o >> h:inHolon :H .

The reified-triple form << :s :p :o >> is itself sugar in Turtle 1.2 [[RDF12-TURTLE]] — it allocates a fresh blank-node reifier related to the triple term <<( :s :p :o )>> via rdf:reifies. The membership expansion produces three triples per asserted triple event (base assertion, rdf:reifies, h:inHolon); a source statement that expands to several triples yields that many events, as shown below.

Reified-triple sugar (left) and the fully-expanded form (right) for the outer @holon ex:Car_123 block.

# Reified-triple sugar
ex:Engine_456 ex:componentOf ex:Car_123 .
<< ex:Engine_456 ex:componentOf ex:Car_123 >>
    h:inHolon ex:Car_123 .

# Fully expanded (no syntactic sugar)
ex:Engine_456 ex:componentOf ex:Car_123 .
_:r1 rdf:reifies
    <<( ex:Engine_456 ex:componentOf ex:Car_123 )>> .
_:r1 h:inHolon ex:Car_123 .

The nested @holon ex:Engine_456 block desugars analogously.

Turtle-H is not TriG

Turtle-H is surface syntax for the reifier profile: a Turtle-H processor MUST NOT treat an @holon block as a TriG [[TRIG]] named graph, and desugars it to h:inHolon annotations within a single graph. This is distinct from the dataset profile (RDF-H named graphs), where a holon's content graph is a named graph realized in a dataset and authored with ordinary TriG / GRAPH syntax. Both encode the same content graph (RDF-H conversion); the prohibition here is only that the @holon directive is not itself TriG. The converse is a grammar property (see ), not a normative requirement on TriG processors.

Expansion Algorithm

A Turtle statement can produce several asserted triples. For example, a list produces triples describing its members and links. An asserted triple event is one triple produced while expanding a source statement, before duplicate triples are removed. The ordered sequence of these events is written T. Keeping events separate lets repeated source statements receive distinct reifiers. A collection is a Turtle list written with parentheses. A blank-node property list uses brackets to describe a blank node inline. An annotation adds statements about a reified statement. These Turtle features may each generate additional triples.

  1. Parse top-level Turtle directives and statements using Turtle 1.2 rules. Ordinary asserted triples outside blocks enter G. Top-level management statements are also copied to M: explicit h:Holon or legacy h:CompleteHolon typing, and h:contentGraph, h:parentHolon, h:imports, or h:importsShapes declarations. Statements with those predicates occurring only inside blocks are content, not management declarations.
  2. On every @holon H block, emit H a h:Holon into both G and M, even if the block is empty. This automatic declaration is not filed content unless the source explicitly files the same statement.
  3. Expand each ordinary Turtle statement in a block to its ordered stream of asserted triple events T before adding RDF-H membership. T includes triples generated by collections, blank-node property lists, and Turtle 1.2 reifiers and annotations. A triple term occurring as a term does not assert its inner triple; follow Turtle's own assertion rules.
  4. For each event (s,p,o) in T, emit its base assertion into G and a fresh blank-node reifier with rdf:reifies <<( s p o )>> and h:inHolon H. Every generated list/property/annotation assertion in T is filed. Repeated source assertions generate distinct occurrence reifiers, although G and CG(H) use set semantics.
  5. Do not feed RDF-H-generated declarations or membership triples back into T. Process source statements first, then add membership records. Do not annotate those generated records again.
  6. Process nested blocks with their own holon H and event stream. Nesting creates no parent relation and files no inner content in the outer block.

A parser MUST expose both G and M (as graph outputs or equivalent graph views) and preserve blank-node identity across them. Returning G alone is an incomplete RDF-H processing context. Parsing/expansion does not itself establish registry or hierarchy validity; validate M with RDF-H before registry-aware operations.

Block-generated declarations register empty holons. Combine existing declarations as a set. Repeating a block identifier refers to the same holon; it does not create another holon.

A Turtle collection expands to several triples, and each one is an asserted triple event with its own membership record. The list nodes are ordinary blank nodes shared between G and the triple terms.

@holon ex:H { ex:s ex:items (ex:a ex:b) . }

ex:s ex:items _:l0 .          _:r1 rdf:reifies <<( ex:s ex:items _:l0 )>> ;          h:inHolon ex:H .
_:l0 rdf:first ex:a .         _:r2 rdf:reifies <<( _:l0 rdf:first ex:a )>> ;        h:inHolon ex:H .
_:l0 rdf:rest _:l1 .          _:r3 rdf:reifies <<( _:l0 rdf:rest _:l1 )>> ;         h:inHolon ex:H .
_:l1 rdf:first ex:b .         _:r4 rdf:reifies <<( _:l1 rdf:first ex:b )>> ;        h:inHolon ex:H .
_:l1 rdf:rest rdf:nil .       _:r5 rdf:reifies <<( _:l1 rdf:rest rdf:nil )>> ;      h:inHolon ex:H .
ex:H a h:Holon .              # registration, in G and M, not filed

Turtle-H Grammar

Turtle-H extends Turtle 1.2 [[RDF12-TURTLE]] with one additional alternative on the statement production. Italicized productions (e.g., iri, BLANK_NODE_LABEL, triples) refer to Turtle 1.2 and are not redefined here. 

[H1]   statement       ::=  directive | triples '.' | holonBlock

[H2]   holonBlock     ::=  '@holon' holonId '{' holonContent* '}'

[H3]   holonId        ::=  iri | BLANK_NODE_LABEL

[H4]   holonContent   ::=  triples '.' | holonBlock

Whitespace and comments follow Turtle 1.2 rules; as between Turtle tokens, whitespace between @holon, the holon identifier, and the opening brace is optional where tokenization allows it, as in @holon<https://example.org/H>{ … }. The @holon keyword is case-sensitive. Like @prefix and @base, @holon is recognized only where a statement or block item may begin; after a string literal the same characters are a Turtle language tag, so the two never conflict. Directives (@prefix, @base, PREFIX, BASE) are permitted only at top level; rule H4 excludes them from blocks. Only the @holon spelling is defined; this version has no case-insensitive HOLON form. A blank-node holon identifier is a labeled blank node; the anonymous form [] is not permitted, since nothing could refer to such a holon.

Desugaring. A Turtle-H parser MUST expand each holonBlock by the expansion algorithm, which is the single statement of the rules; the desugaring example shows its result for one statement.

Disambiguation from TriG. The holonBlock begins with @holon, which is not a valid token at the same grammatical position in Turtle 1.2 or TriG [[TRIG]]. A Turtle-H parser MUST NOT treat a TriG named-graph block (iri '{' triples '}') as a holonBlock; conversely, a TriG parser encountering Turtle-H input will reject it as a syntax error. This is a property of the two grammars and imposes no requirements on TriG processors, which are governed by [[TRIG]] and lie outside the scope of this specification.

Serializing to Turtle-H

A Turtle-H serializer writes reifier-profile data G with its metadata context M as a Turtle-H document. It is the inverse of expansion only for the membership records that expansion generates. Serialization stays within the reifier profile; it is not a representation conversion in the RDF-H sense, so the RDF-H conversion rules on preserving M do not apply to the differences listed below.

  1. A reifier MAY be folded into an @holon block only when it is a blank node, its only properties are exactly one rdf:reifies and exactly one h:inHolon, its triple term's base triple is asserted in G, and no other statement in G or M mentions the reifier. The base triple is written inside the block for the holon named by h:inHolon, and its membership record and redundant top-level base assertion are omitted.
  2. Every other reifier, including IRI reifiers, reifiers with occurrence metadata, and reifiers filed in several holons through several rdf:reifies values, MUST be written expanded, as ordinary Turtle 1.2 statements outside any block.
  3. Several foldable reifiers for the same base triple and holon MAY be written as that many repeated statements in the block; a serializer that writes them once MUST declare that it does not preserve occurrence multiplicity.
  4. A holon registered in M is written as an @holon block, empty if it has no foldable members. Management statements of M are written as top-level statements (in addition to any block in which the same statement is filed), so that re-parsing recovers them into M. Other statements of M are written at top level too, but a re-parse places them only in G; a serializer MUST report that M is reduced to its management statements.
  5. Blank-node holons keep one label across M, blocks, and expanded statements, since the document is one blank-node scope.

A serializer MUST NOT promote a management assertion absent from M into M on re-parsing. If such an assertion would have to be written at top level because no existing eligible occurrence is folded to carry it solely inside a block, the serializer MUST reject the context with unrepresentable-context. It must not invent a membership to hide the assertion. This is a serialization failure, not a Turtle-H syntax error. More generally, it must reject any context that cannot meet the preservation contract below.

For a successful serialization, re-parsing yields G and M equal to the inputs up to the documented differences: folded reifiers receive fresh blank-node labels; every block adds an H a h:Holon registration to both G and M, so a holon registered only through h:contentGraph or lacking that typing in G gains it; M is reduced to its management statements; and occurrence multiplicity may be reduced only under the declaration required above. Folding is optional, block grouping and statement order are not canonical, and two conforming serializers need not produce identical blocks.

This specification defines three conformance classes. A Turtle-H document is a Unicode string, encoded in UTF-8, that conforms to the grammar. A Turtle-H parser reads such documents and produces G and M. A Turtle-H serializer writes such documents from G and M.

A conforming Turtle-H parser MUST recognize the grammar and perform the desugaring defined above, emitting both base assertions and RDF-H membership annotations. The restrictions distinguishing @holon from TriG also apply. A conforming Turtle-H serializer MUST follow the folding rules above, reject unrepresentable contexts, and declare whether it preserves occurrence multiplicity.

RDF-H graph and processor conformance are defined in RDF-H. The suite includes positive and negative syntax, expansion, and serialization tests. A positive serialization test supplies G and M, and the serializer's output, re-parsed by the same implementation, must reproduce them within the documented differences. Negative serialization tests require the defined representability rejection; broader base-language coverage remains future work.

The RDF test manifest uses W3C manifest infrastructure with project-specific Turtle-H test classes. See the suite guide for implementation adapters, result comparison, and EARL reporting. Manifest integrity and expected-result smoke checks do not establish parser conformance, and no Turtle-H parser is bundled with the suite. The RDF4J-based rdf4j-rio-turtleh codecs execute all 81 cases through the suite adapter and pass them, including 22 successful serialization tests and one representability rejection; it is maintained by the editors' organization and is not independent interoperability evidence.

Expansion conformance includes the staged rules in the expansion algorithm, both output graphs, RDF 1.2 directional literals, collections, property lists, and annotations. The inherited Turtle grammar is normative; a subset implementation must declare unsupported features rather than claim full Turtle-H conformance.

The extension suite exercises the parser and serializer rules above; inherited Turtle 1.2 grammar coverage is not established. Deployment and documentation duties are assessed by review: the media-type rule and a serializer's duties to declare how it handles occurrence multiplicity and to report a reduced M, which concern documentation. The effect of that reduction on a re-parse is tested.

Internationalization: Turtle-H adds the ASCII keyword @holon and no string-bearing construct. Literals, language tags, directional literals, and non-ASCII IRIs are handled by the inherited Turtle 1.2 rules and pass through expansion unchanged. Security considerations are those of Turtle 1.2 and of RDF-H, with one addition: the grammar lets blocks nest without limit, and each level holds parser state, so a parser reading untrusted input SHOULD bound the nesting depth and reject deeper documents as a syntax error.

Media Type and File Extension

No media type is registered for Turtle-H. Documents containing @holon blocks MUST NOT be served as text/turtle, since ordinary Turtle parsers reject them. The following registration template records the intended registration; it is a proposal and the type is not yet registered.

Type name
text
Subtype name
turtle-h (proposed)
Required parameters
None
Optional parameters
None. The encoding is always UTF-8, so no charset parameter is defined, as for text/turtle.
Encoding considerations
The syntax is expressed over Unicode and encoded in UTF-8, as for Turtle.
Security considerations
Those of text/turtle apply. Turtle-H additionally produces metadata that registers holons; consumers treat that metadata as untrusted data unless the document source is trusted, as described in the RDF-H security considerations.
Interoperability considerations
Turtle-H documents without @holon blocks are Turtle 1.2 documents. Documents with blocks are not accepted by Turtle or TriG parsers.
Published specification
This document.
Applications that use this media type
RDF-H processors and tools that author holon content.
Fragment identifier considerations
As for text/turtle: a fragment identifier, resolved against the document IRI, identifies an RDF resource. Fragment identifiers do not address @holon blocks.

File extension: .ttlh. Macintosh file type code: TEXT.
